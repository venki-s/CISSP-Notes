# Chapter 14 — Controlling and Monitoring Access

**CISSP Domains:** 3.7, 5.4, 5.5, 5.6

---

## 1. Access Control Fundamentals

### Permissions, Rights, and Privileges
- **Permission:** Allowed operation on an object (read, write, execute).
- **Right:** Ability to perform a system action (restore backup, change system time).
- **Privilege:** Elevated rights and permissions.

### Fundamental Principles
- **Need to Know:** Grant access only to information required for job duties.
- **Separation of Duties (SoD):** Divide sensitive operations among multiple individuals to prevent fraud and errors.

**Exam:** Security clearance alone does not establish need to know.

---

## 2. Authorization Mechanisms

| Mechanism | Key Concept |
|---|---|
| Access Control Matrix | Table mapping subjects, objects, and permitted operations |
| Access Control List (ACL) | Object-focused: Who can access this object? |
| Capability List | Subject-focused: Which objects can this subject access? |
| Constrained Interface | Restricts available application functions |
| Content-Dependent | Access depends on information within the resource |
| Context-Dependent | Access depends on circumstances surrounding the request |

### Important Distinctions
- **ACL:** Permissions associated with an object.
- **Capability List:** Access capabilities associated with a subject.
- **Content:** Database view exposes selected fields.
- **Context:** Access permitted only during business hours or after completing a workflow.

**Exam Trap:** Hiding a function in the UI is not sufficient; authorization must still be enforced.

## 3. Access Control Models

| Model | Access Determined By | Key Characteristic |
|---|---|---|
| DAC | Object owner | Owner grants/revokes access |
| RBAC | Job role | Permissions assigned to roles |
| Rule-Based | Global rules | Rules apply to subjects |
| ABAC | Multiple attributes | Fine-grained policy decisions |
| MAC | Security labels | Centrally enforced classifications |
| Risk-Based | Assessed risk | Dynamic access decisions |
| TBAC | Assigned tasks | Access tied to work tasks |

### 3.1 Discretionary Access Control (DAC)
- Every object has an owner.
- Owner controls permissions, commonly through ACLs.
- Flexible but susceptible to inappropriate permission sharing.
- Example: Owner grants another user access to a file.

**Exam:** Owner determines access → DAC.

### 3.2 Role-Based Access Control (RBAC)
- Administrators assign permissions to roles.
- Users inherit permissions through role membership.
- Roles generally correspond to job functions.
- Simplifies provisioning and revocation.
- Helps prevent **privilege creep**.

**Privilege Creep:** Accumulation of unnecessary permissions as job responsibilities change.

**Exam:** Access based on job responsibilities → RBAC.

### 3.3 Rule-Based Access Control
- Uses centrally defined rules or restrictions.
- Rules generally apply across subjects.
- Common example: Firewall ACL with implicit deny.

**Exam:** Global firewall restrictions → Rule-Based.

### 3.4 Attribute-Based Access Control (ABAC)
- Evaluates combinations of attributes:
  - Subject: Role, department, clearance.
  - Object: Classification, sensitivity.
  - Environment: Time, location, device.
  - Action: Read, write, delete.
- Supports dynamic, fine-grained authorization.

**Exam:** Department + compliant device + business hours → ABAC.

### 3.5 Mandatory Access Control (MAC)
- Uses security labels assigned to subjects and objects.
- Access decisions are centrally enforced.
- Users cannot independently modify access permissions.
- Supports classification and compartmentalization.
- Enforces need to know.

**Exam:** Clearance and classification labels → MAC.

#### MAC Environments
- **Hierarchical:** Ordered security levels (Top Secret > Secret > Confidential).
- **Compartmentalized:** Independent security domains requiring specific authorization.
- **Hybrid:** Combines hierarchical levels and compartments.

**Important:** Higher clearance does not automatically grant access to every compartment.

### 3.6 Risk-Based Access Control
- Evaluates risk using:
  - User behavior.
  - Location and IP address.
  - Device compliance.
  - Threat intelligence.
  - Authentication strength.
- Can allow, deny, restrict, or require additional authentication.
- May use machine learning to identify unusual activity.

**Exam:** Unusual login triggers step-up MFA → Risk-Based.

### 3.7 Task-Based Access Control (TBAC)
- Permissions depend on assigned tasks rather than job roles.

**Exam:** Access to specific assigned project tasks → TBAC.

### Model Comparison — Exam Traps
- DAC vs. RBAC: Owner controls access vs. administrator assigns permissions to roles.
- RBAC vs. Rule-Based: Job function vs. predefined global rules.
- ABAC vs. Risk-Based: Attribute evaluation vs. adaptive risk assessment.
- MAC vs. DAC: Centralized label enforcement vs. owner discretion.

## 4. SSO and Federated Authentication

### Single Sign-On (SSO)
- Authenticate once to access multiple authorized services.

### Federated Identity Management (FIM)
- Establishes identity trust between separate security domains or organizations.

### SAML vs. OAuth vs. OIDC

| Technology | Primary Purpose | Mechanism |
|---|---|---|
| SAML | Federated authentication and SSO | XML assertions |
| OAuth 2.0 | Delegated authorization | Access tokens |
| OIDC | Authentication using OAuth 2.0 | ID tokens (typically JWT) |

### SAML
- XML-based standard.
- Three entities:
  - **Principal:** User.
  - **Identity Provider (IdP):** Authenticates user.
  - **Service Provider (SP):** Provides requested service.
- SAML assertions can contain:
  - Authentication statements.
  - Attribute statements.
  - Authorization decision statements.

**Exam:** XML assertion exchanged between IdP and SP → SAML.

### OAuth 2.0
- Authorization framework, **not an authentication protocol**.
- Enables delegated resource access without sharing user passwords.
- Uses authorization/access tokens.

**Exam:** Third-party application receives permission to access an API → OAuth.

### OpenID Connect (OIDC)
- Authentication layer built on OAuth 2.0.
- Uses ID tokens to communicate authentication information.
- Supports authentication alongside OAuth authorization.

**Exam:** OAuth-based login using an ID token → OIDC.

**Critical:** ID token proves authentication; access token authorizes resource access.

## 5. AAA Protocols

**AAA = Authentication, Authorization, Accounting**

- Authentication: Verify identity.
- Authorization: Determine permitted access.
- Accounting: Record usage and activities.

### Kerberos
- Ticket-based authentication protocol.
- Provides SSO and supports mutual authentication.
- Uses symmetric cryptography.
- Common in Active Directory.

#### Components
- **KDC:** Key Distribution Center; trusted authentication authority.
- **AS:** Authentication Service; performs initial authentication.
- **TGS:** Ticket-Granting Service; issues service tickets.
- **TGT:** Ticket-Granting Ticket; used to request service tickets.
- **Service Ticket:** Used to authenticate to a particular service.
- **Principal:** Kerberos identity.
- **Realm:** Kerberos administrative domain.

#### Authentication Flow
1. Client authenticates with AS.
2. AS issues TGT.
3. Client presents TGT to TGS.
4. TGS issues service ticket.
5. Client presents service ticket to resource server.

**Remember:** AS → TGT → TGS → Service Ticket → Resource.

#### Security Considerations
- Password is not transmitted in plaintext.
- Tickets have limited lifetimes.
- Requires clock synchronization (commonly within 5 minutes).
- KDC is a critical security dependency.
- Uses TCP/UDP port **88**.

**Exam:** Kerberos authenticates identities; resource authorization is still required.

### RADIUS
- Centralized AAA for network access (VPN, remote access).
- Network Access Server (NAS) acts as RADIUS client.
- Traditional RADIUS protects password information, not the entire packet.
- Uses UDP:
  - **1812:** Authentication/authorization.
  - **1813:** Accounting.

### TACACS+
- Centralized AAA, commonly for network device administration.
- Separates authentication, authorization, and accounting.
- Supports granular command authorization.
- Traditional TACACS+ encrypts the packet body.
- Uses **TCP 49**.

### RADIUS vs. TACACS+

| RADIUS | TACACS+ |
|---|---|
| Network access | Device administration |
| UDP 1812/1813 | TCP 49 |
| AAA functions more closely coupled | AAA functions separated |
| Protects password field | Encrypts packet body |

## 6. Zero-Trust Access Enforcement

### Core Principles
- Do not trust solely based on network location.
- Verify access requests.
- Enforce least privilege.
- Evaluate identity, device posture, and security context.
- Reassess access when conditions change.

### Components

| Component | Responsibility |
|---|---|
| Policy Engine (PE) | Makes allow/deny/revoke decisions |
| Policy Administrator (PA) | Establishes or terminates communication paths |
| Policy Decision Point (PDP) | Logical combination of PE + PA |
| Policy Enforcement Point (PEP) | Enforces access decisions |

### Access Flow
Subject → PEP → PDP decision → PEP enforcement → Resource

**Exam Traps**
- Who makes the access decision? **Policy Engine**
- Who establishes/terminates the communication path? **Policy Administrator**
- Who enforces access decisions? **Policy Enforcement Point**
- What constitutes the PDP? **PE + PA**

## 7. Privilege Escalation

### Vertical Privilege Escalation
- Gaining higher privileges.
- Example: Standard user → Administrator.

### Horizontal Privilege Escalation
- Gaining unauthorized access to another account at a similar privilege level.
- Example: User A accesses User B's account.

### Lateral Movement
- Moving from one compromised system to another.

**Exam:** Vertical = Up; Horizontal = Across accounts; Lateral = Across systems.

### Service Account Security
- Apply least privilege.
- Avoid unnecessary LocalSystem privileges.
- Use dedicated service accounts.
- Restrict and monitor privileged access.

### Linux: su vs. sudo
- **su:** Switches user identity, commonly to root.
- **sudo:** Runs authorized commands with elevated privileges using the invoking user's identity.
- sudo supports granular delegation and improved individual accountability.

**Exam:** Controlled elevation with auditable individual commands → sudo.

### PowerShell Abuse
- Legitimate administrative tool that attackers may misuse.
- Can support fileless execution and privilege escalation.
- Execution policy is not a strong security boundary.

**Controls:** Least privilege, application control, endpoint monitoring, and logging.

## 8. Password Attacks

| Attack | Key Characteristic |
|---|---|
| Dictionary | Tries passwords from predefined lists |
| Brute Force | Systematically tries combinations |
| Hybrid | Dictionary words plus variations |
| Password Spraying | One/few passwords across many accounts |
| Credential Stuffing | Reuses stolen username/password pairs |
| Birthday | Attempts to find hash collisions |
| Rainbow Table | Uses precomputed hash information |

### Critical Distinctions
- **Spraying:** One password → Many accounts.
- **Stuffing:** Stolen credentials → Other services.
- **Dictionary:** Predefined wordlist.
- **Brute Force:** Exhaustive combinations.
- **Hybrid:** Dictionary + character modifications.
- **Birthday:** Hash collision.
- **Rainbow Table:** Precomputed password hashes.

### Online vs. Offline Attacks
- **Online:** Attempts authentication against a live system; subject to lockout and rate limiting.
- **Offline:** Attacker cracks stolen password hashes without contacting the authentication system.

**Exam:** Account lockout does not stop offline password cracking.

---

## 9. Password Hashing Protections

### Hash
- One-way transformation used for password verification.

### Salt
- Unique random value used when hashing a password.
- Prevents effective reuse of generic rainbow tables.
- Typically stored with the password hash.

### Pepper
- Additional secret used in password protection.
- Stored separately from the password database.

### Password Hashing Algorithms
- Argon2.
- bcrypt.
- PBKDF2.

### Important
- MD5 is unsuitable for secure password storage.
- General-purpose fast hashes are not ideal for password hashing.
- Password-specific hashing algorithms increase the cost of offline guessing.

**Exam:** Rainbow table mitigation → Unique salts and appropriate password hashing.

## 10. Mimikatz and Credential Theft

### Mimikatz
- Tool capable of extracting Windows authentication material.
- Can obtain credentials, hashes, and Kerberos tickets under suitable conditions.
- Commonly associated with LSASS credential access.

### LSASS
- Windows process involved in authentication and security enforcement.
- May contain sensitive authentication material.

### Mitigations
- Protect credentials in memory.
- Restrict administrative access.
- Apply least privilege.
- Monitor suspicious credential access.
- Use supported credential isolation protections.

**Exam:** Credential extraction from Windows memory → Mimikatz.

## 11. Pass-the-Hash and Kerberos Exploitation

| Attack | Mechanism |
|---|---|
| Pass-the-Hash (PtH) | Reuse stolen NTLM hash for authentication |
| Overpass-the-Hash | Use stolen key material to obtain Kerberos authentication |
| Pass-the-Ticket | Reuse stolen Kerberos ticket |
| Silver Ticket | Forge Kerberos service ticket |
| Golden Ticket | Forge TGT using KRBTGT key |
| ASREPRoasting | Crack AS response when preauthentication is disabled |
| Kerberoasting | Obtain service-ticket material for offline cracking |
| Kerberos Brute Force | Guess usernames/passwords |

### Pass-the-Hash
- Does not require plaintext password.
- Commonly exploits reusable NTLM authentication material.
- Can enable lateral movement.

**Exam:** Stolen hash used directly for authentication → PtH.

### Pass-the-Ticket
- Reuses an existing Kerberos ticket.

**Exam:** Stolen ticket used to impersonate a user → PtT.

### Silver Ticket
- Forged service ticket.
- Typically requires compromised service account key.
- Usually targets a particular service.

### Golden Ticket
- Forged TGT.
- Requires compromised KRBTGT key material.
- Can enable extensive domain-wide impersonation.

**Exam:** KRBTGT compromise → Golden Ticket.

### ASREPRoasting
- Targets accounts without Kerberos preauthentication.
- Obtains encrypted AS response material for offline cracking.

**Exam:** Disabled preauthentication → ASREPRoasting.

### Kerberoasting
- Obtains encrypted service-ticket material.
- Attempts offline cracking of service-account credentials.
- Targets accounts associated with service principal names (SPNs).

**Exam:** Service-ticket cracking → Kerberoasting.

### Attack Mitigations
- Strong service account credentials.
- Managed service accounts.
- Kerberos preauthentication.
- Restrict administrative privileges.
- Protect domain controllers and KRBTGT.
- Reduce NTLM usage.
- Monitor suspicious ticket activity.

## 12. Sniffing and Spoofing

### Sniffing
- Capturing network packets.
- May expose plaintext credentials and sensitive information.
- Also called eavesdropping or snooping.

**Mitigations**
- Encrypt sensitive traffic.
- Use HTTPS, SSH, and SFTP instead of insecure alternatives.
- Protect network infrastructure.

**Exam:** Packet capture revealing plaintext credentials → Sniffing.

### Spoofing
- Impersonating another identity or source.

**Examples**
- IP spoofing.
- Email spoofing.
- Caller ID spoofing.
- Fake login screens.

**Mitigations**
- Strong authentication.
- Email authentication controls.
- Independent verification of sensitive requests.
- Security awareness.

**Exam:** Falsifying identity/source information → Spoofing.

## 13. Core Access Control Countermeasures

| Control | Primary Purpose |
|---|---|
| Least Privilege | Reduce impact of compromised accounts |
| MFA | Reduce password-only account compromise |
| Account Lockout | Limit online guessing |
| Rate Limiting | Restrict repeated authentication attempts |
| Salted Password Hashing | Resist offline cracking and rainbow tables |
| Credential Isolation | Reduce credential theft from memory |
| Unique Passwords | Prevent credential stuffing |
| Access Reviews | Detect privilege creep |
| Logging/Auditing | Detect unauthorized activity |
| Network Encryption | Protect against cleartext sniffing |
| Physical Security | Prevent direct access to protected systems |
| Security Awareness | Reduce phishing and social engineering risks |

### Important Limitations
- Account lockout does not prevent offline attacks.
- Encryption prevents reading captured traffic, not packet capture itself.
- MFA reduces credential-based compromise but is not immune to all attacks.
- Least privilege limits the impact of successful compromise.
