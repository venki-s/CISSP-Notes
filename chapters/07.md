## 1. Asymmetric (Public-Key) Cryptography

**Asymmetric cryptography** uses a mathematically related **public/private key pair**. The public key can be distributed freely; the private key must be protected. It solves much of the key-distribution challenge of symmetric encryption but is slower, so it is often combined with symmetric encryption.

| Purpose | Key used | Easy memory |
|---|---|---|
| **Confidentiality — encrypt** | **Recipient's public key** | Anyone can lock a message *for* the recipient. |
| **Confidentiality — decrypt** | **Recipient's private key** | Only the recipient can unlock it. |
| **Digital signature — sign** | **Sender's private key** | Only the sender should be able to sign. |
| **Digital signature — verify** | **Sender's public key** | Anyone with the trusted public key can verify. |

**Example:** Alice encrypts a file using Bob's public key; Bob decrypts it using his private key. To sign a document, Alice signs its digest with her private key, and Bob verifies using Alice's public key.

<mark class="confident"/>**CISSP exam clue:** **Recipient's keys → confidentiality**; **sender's keys → signature, integrity, origin authentication, nonrepudiation** (assuming the private key is protected and identity is trustworthy). Signing does **not** automatically encrypt the message.


### <mark class="confident"/>Important Asymmetric Algorithms

| Algorithm | How it works / significance | CISSP clue |
|---|---|---|
| **Rivest–Shamir–Adleman (RSA)** | Uses two very large prime numbers multiplied together. Multiplication is easy, but factoring the resulting huge number into its original primes is computationally difficult, forming the basis of RSA security. Supports **public-key encryption and digital signatures**. **Example:** Alice encrypts a message using Bob's public key, and only Bob's private key can decrypt it. | **Prime factorization → RSA**. Encryption uses the recipient's public key; signing uses the sender's private key. |
| **Diffie–Hellman (DH)** | Allows two parties to **establish the same shared secret over an insecure network without transmitting the secret itself**. Each party combines its own private value with publicly exchanged values to independently calculate the same secret. **Example:** Two servers establish a shared encryption key over the internet, even though an attacker can observe the exchange. DH establishes keys; it does **not encrypt application data**. | **Shared secret establishment → DH**. The secret itself never travels across the network. |
| **Ephemeral Diffie–Hellman (DHE)** | A variation of DH that generates **temporary private key material for each session**, rather than reusing long-term DH keys. This helps provide **Perfect Forward Secrecy (PFS)**, meaning that compromising a server's long-term authentication key later does not reveal previously recorded session traffic. **Example:** If a server's certificate private key is stolen tomorrow, properly protected previous DHE sessions remain confidential. | **Temporary DH keys → DHE → Perfect Forward Secrecy (PFS)**. |
| **Elliptic Curve Cryptography (ECC)** | A family of asymmetric cryptographic techniques based on the **Elliptic Curve Discrete Logarithm Problem (ECDLP)**, which is computationally difficult to reverse. ECC provides comparable classical security to RSA using **much smaller keys**, reducing computation, storage, and communication overhead. **Example:** A 256-bit ECC key provides approximately the same classical security strength as a 3,072-bit RSA key. Useful in mobile and resource-constrained devices. | **Smaller keys + comparable security → ECC**. ECC is a family of techniques, not a single encryption algorithm. |
| **Elliptic Curve Diffie–Hellman Ephemeral (ECDHE)** | Combines **ECC mathematics with ephemeral Diffie–Hellman key agreement**. Two parties use temporary elliptic-curve key pairs to establish a shared session secret efficiently, providing Perfect Forward Secrecy when properly implemented. **Example:** Modern Transport Layer Security (TLS) connections commonly use ECDHE to establish session secrets, then use symmetric encryption to protect the actual data. | **ECC + DH + temporary keys → ECDHE**. Efficient key agreement with Perfect Forward Secrecy. |
| **ElGamal** | An asymmetric encryption algorithm developed from the mathematical principles behind Diffie–Hellman, using the difficulty of the **Discrete Logarithm Problem (DLP)**. Unlike DH, which establishes a shared secret, ElGamal can **encrypt actual messages** and has related signature schemes. Its ciphertext consists of two components and can be significantly larger than the plaintext. | **DH-related mathematics + public-key encryption → ElGamal**. Remember: DH agrees on keys; ElGamal encrypts data. |
| **Merkle–Hellman Knapsack** | An early asymmetric encryption algorithm based on the mathematical **knapsack problem**, using a super-increasing sequence of numbers to create public and private keys. It was successfully cryptanalyzed and is no longer considered secure. **Example:** An attacker exploits mathematical weaknesses to recover information that the algorithm was intended to protect. | **Knapsack problem → Merkle–Hellman → Broken historical algorithm**. |

**Approximate Classical Security Equivalence:**

| Symmetric Encryption | RSA | ECC |
|---|---|---|
| **128-bit key** | **3,072-bit key** | **256-bit key** |

**Important:** Equal key lengths do not mean equal security across different algorithms. ECC achieves comparable classical security to RSA with substantially smaller keys because the underlying mathematical problems differ.

**Diffie–Hellman Security Limitation:** Basic, unauthenticated DH is vulnerable to a **Man-in-the-Middle (MITM)** attack because it establishes a shared secret without verifying the other party's identity. An attacker can negotiate separate keys with Alice and Bob, intercepting their communications. **Mitigation:** Use authenticated key exchange, such as certificate-authenticated TLS.

**Easy Memory:**
- **RSA → Prime factorization → Encryption and signatures.**
- **DH → Establish a shared secret.**
- **DHE → DH with temporary keys → Forward secrecy.**
- **ECC → Smaller keys, comparable classical security.**
- **ECDHE → ECC + DH + temporary keys.**
- **ElGamal → DH-related mathematics used for encryption.**
- **Merkle–Hellman → Broken knapsack cryptosystem.**

## 2. Quantum Cryptography and Post-Quantum Risk

| Concept | Explanation and example |
|---|---|
| **Quantum computing** | Uses **qubits (quantum bits)**. Sufficiently capable quantum computers could undermine traditional public-key systems such as RSA and DH by solving their mathematical problems more efficiently. |
| **Quantum Key Distribution (QKD)** | Uses quantum-physics principles to distribute key material and make certain interception attempts detectable. It requires specialized infrastructure; it is **not the same** as an ordinary software-based post-quantum algorithm. |
| **Post-Quantum Cryptography (PQC)** | Cryptographic algorithms designed to resist attacks from both conventional and quantum computers. Organizations should plan for long-lived data that attackers could **harvest now and decrypt later**. |

**CISSP clue:** Quantum risk is especially significant for **RSA, DH, and traditional ECC**. Assess **how long information needs to remain confidential**, not only whether it is secure today.

## 3. Cryptographic Hash Functions

A **hash function** converts data of almost any input length into a **fixed-length message digest (hash value/fingerprint)**. Changing even one input bit should generally change the digest substantially (**avalanche effect**). Hashing is **one-way**, not reversible decryption, and provides no confidentiality.

**Desired properties:** (1) accepts variable-length input, (2) fixed-length output, (3) efficient to calculate, (4) preimage resistant (hard to recover an input from its hash), and (5) collision resistant (hard to find two different inputs producing the same hash). A **collision** means two different inputs produce the same digest.

**Example:** A software vendor publishes a file and its SHA-256 hash. You hash the downloaded file and compare values; a mismatch means the file differs. **Important:** A hash received from an untrusted source does not itself authenticate the sender—an attacker might replace both the file and its hash.

### Hash algorithm comparison

| Algorithm | Digest size | Status / CISSP distinction |
|---|---:|---|
| **Message Digest 5 (MD5)** | **128 bits** | Broken collision resistance; unsuitable for security-sensitive integrity or signatures. |
| **Secure Hash Algorithm 1 (SHA-1)** | **160 bits** | Known collision attacks; deprecated for security-sensitive signatures. |
| **Secure Hash Algorithm 2 (SHA-224)** | **224 bits** | Member of the SHA-2 family. |
| **Secure Hash Algorithm 2 (SHA-256)** | **256 bits** | Widely used secure hash. |
| **Secure Hash Algorithm 2 (SHA-384)** | **384 bits** | Member of the SHA-2 family. |
| **Secure Hash Algorithm 2 (SHA-512)** | **512 bits** | Member of the SHA-2 family. |
| <mark class="confident"/>**Secure Hash Algorithm 3 (SHA3-224/256/384/512)** | <mark class="confident"/>**224/256/384/512 bits** | <mark class="confident"/>Keccak-based alternative family, structurally different from SHA-2. |
| <mark class="confident"/>**RACE Integrity Primitives Evaluation Message Digest 160 (RIPEMD-160)** | <mark class="confident"/>**160 bits** | <mark class="confident"/>Alternative hash family; primarily recognize its name and digest size. |
| <mark class="confident"/>**Hashing Algorithm with Variable Length (HAVAL)** | <mark class="confident"/>**128/160/192/224/256 bits** | <mark class="confident"/>Older variable-digest-length family. |
| <mark class="confident"/> **Hash-Based Message Authentication Code (HMAC)** | <mark class="confident"/>**Depends on the underlying hash** | <mark class="confident"/>Combines a hash function with a **shared secret key**; not a standalone fixed-output-length hash algorithm. |

<mark class="confident"/> **HMAC (Hash-Based Message Authentication Code):** A sender computes a **keyed** message authentication code using a shared secret and hash function; the receiver verifies it with the same secret. Provides **integrity and message authentication between holders of the key**, but **not nonrepudiation**, because either holder could have generated it.

**CISSP exam clue:** **Hash alone → integrity check** (if reference is trustworthy); **HMAC → integrity + shared-key authentication**; **digital signature → integrity + origin authentication + nonrepudiation**, with appropriate trust controls.

## 4. Digital Signatures and the Digital Signature Standard

A **digital signature** combines hashing and asymmetric cryptography. It does not, by itself, keep a message secret.

1. **Sender:** Calculate a hash of the message and **sign the digest with the sender's private key**.
2. **Receiver:** Verify the signature using the **sender's public key**, and compare the verified digest with the hash of the received message.
3. **Result:** A valid signature helps establish **message integrity, origin authentication, and nonrepudiation**, assuming the signing key and associated identity are trustworthy.

**Example:** A software vendor digitally signs an update. Your system verifies the signature using the vendor's trusted public key, helping detect tampering and impersonation.

| Security goal | Cryptographic mechanism |
|---|---|
| **Confidentiality** | Encrypt to the **recipient's public key** (or use authenticated symmetric encryption). |
| **Integrity only** | Hash comparison against a **trusted** digest. |
| <mark class="confident"/> **Integrity + shared-key authentication** |<mark class="confident"/> **Hash-Based Message Authentication Code (HMAC)**. |
| <mark class="confident"/>**Integrity + origin authentication + nonrepudiation** | <mark class="confident"/>**Asymmetric digital signature**. |
| <mark class="confident"/>**All four goals** |<mark class="confident"/> Combine **encryption and digital signature** (with proper key/certificate verification). |

<mark class="confident"/>**Digital Signature Standard (DSS):** **Federal Information Processing Standard (FIPS) 186-5**, issued by the **National Institute of Standards and Technology (NIST)**, specifies conventional digital-signature schemes including **RSA**, **Elliptic Curve Digital Signature Algorithm (ECDSA)**, and **Edwards-Curve Digital Signature Algorithm (EdDSA)**. The legacy **Digital Signature Algorithm (DSA)** is retained for verifying older signatures rather than creating new ones under this revision.

**CISSP clue:** A digital signature is **not the same as encryption**. The sender signs with their **own private key**; the receiver verifies with the **sender's public key**.

## 5. Public Key Infrastructure (PKI) and Certificates

**Public Key Infrastructure (PKI)** is the people, technology, rules, and processes for binding **public keys to trusted identities** through digital certificates. A **certificate does not contain the subject's private key**; it carries their public key and identity/usage details, signed by a trusted issuer.

| PKI component | What it does / example |
|---|---|
| **Certificate Authority (CA)** | Issues and digitally signs certificates, binding a public key to an identity or domain. Its **private signing key is extremely sensitive**. |
| **Root CA (Root Certificate Authority)** | The **highest trusted authority** in a certificate hierarchy. It signs and authorizes intermediate CAs and is usually self-signed. Its private key is often kept **offline** to prevent compromise. |
| **Intermediate CA (Intermediate Certificate Authority)** | A CA trusted and authorized by the Root CA to issue certificates to websites, users, or other CAs. It handles everyday certificate issuance so the **Root CA remains protected**. |
| **Certificate Chain / Chain of Trust** | A sequence of certificates connecting a website's certificate to a trusted Root CA. **Example:** Website Certificate → Intermediate CA → Root CA. Each certificate is checked to establish trust. |
| **Certificate Signing Request (CSR)** | A request sent to a CA to obtain a digital certificate. It contains the applicant's **public key and identity details** and is normally signed using the corresponding private key. |
| **X.509 Certificate** | A standard format for digital certificates that links an identity (such as a website) to its **public key**. Contains details such as the subject, issuer, validity period, public key, and CA signature. |
| <mark class="confident"/>**Certificate Practice Statement (CPS)** | <mark class="confident"/>A document explaining **how a CA operates**, including how it verifies identities, issues certificates, protects keys, and revokes certificates. |



### X.509 certificate — fields to recognize

| Field | Purpose |
|---|---|
| **Version / serial number** | Format version and CA-assigned unique certificate identifier. |
| **Issuer** | Identity of the **CA** signing the certificate. |
| **Subject** | Identity of the entity holding the public key. |
| **Subject Public Key** | Public key associated with the subject; **not** the private key. |
| **Validity period** | **Not Before / Not After** dates. |
| **Signature algorithm / CA signature** | Technique used and cryptographic signature authenticating certificate contents. |
| <mark class="confident"/>**Subject Alternative Name (SAN)** | <mark class="confident"/>Additional domain names or other certified identities; important when checking website names. |

<mark class="confident"/>**Wildcard example:** A certificate for `*.example.org` ordinarily covers `www.example.org` and `mail.example.org`, **not** the apex `example.org` or deeper name `a.b.example.org` unless separately listed.

### Certificate enrollment, verification, and revocation

1. **Enrollment:** Applicant proves appropriate identity/domain control; generates or possesses a key pair and submits a **Certificate Signing Request (CSR)**.
2. **Issuance:** The **Certificate Authority (CA)** creates and signs the **X.509** certificate using the CA's **private key**.
3. **Verification:** Client checks the **trusted certificate chain and signatures**, **hostname/identity**, **validity dates**, **permitted usage**, and **revocation status** as appropriate.
4. **Revocation:** CA invalidates a certificate before expiration when, for example, a private key is compromised, identity changes, or a certificate was issued incorrectly.

**Certificate types:** **Domain Validation (DV)** certificates establish domain control; **Extended Validation (EV)** certificates add organizational identity checks. **EV does not mean stronger encryption**.

| Revocation approach | Explanation / limitation |
|---|---|
| **Certificate Revocation List (CRL)** | CA publishes a signed list of revoked certificate serial numbers. **Disadvantage:** Lists can become stale between downloads/updates. |
| **Online Certificate Status Protocol (OCSP)** | Client/responder checks certificate status (**good, revoked, unknown**) using an online responder. Reduces dependence on periodic CRL downloads. |
| <mark class="confident"/>**OCSP Stapling (Online Certificate Status Protocol Stapling)** | <mark class="confident"/>The website's server obtains a **recent, digitally signed certificate-status response from the Certificate Authority (CA)** and sends it to the browser during the secure connection. This allows the browser to check whether the certificate is revoked **without contacting the CA separately**, improving speed and reducing CA server load. |
| <mark class="confident"/>**Certificate Pinning** | <mark class="confident"/>An application is configured to **trust only a specific certificate or public key** for a website or server. If an attacker presents a different certificate, even one issued by a trusted CA, the application can reject the connection. **Risk:** Legitimate certificate or key changes can break connectivity if the pin is not updated. |


**CISSP exam clue:** Identity verification before certificate issuance → **RA**; actual signing/issuance → **CA**; **revoked list → CRL**; **online status request → OCSP**; **server provides OCSP response → stapling**.

### Certificate file formats

| Format | Common extensions | Distinction |
|---|---|---|
|<mark class="confident"/>**Distinguished Encoding Rules (DER)** | <mark class="confident"/>`.der`, `.cer`, `.crt` | <mark class="confident"/>**Binary** encoded certificates. |
| <mark class="confident"/>**Privacy-Enhanced Mail (PEM)** |<mark class="confident"/> `.pem`, `.crt` | <mark class="confident"/>**Base64 text** with headers such as `BEGIN CERTIFICATE`. |
| <mark class="confident"/>**Personal Information Exchange (PFX), often PKCS #12** |<mark class="confident"/> `.pfx`, `.p12` | <mark class="confident"/>Binary container that may bundle certificate(s) **and a private key**, usually password-protected. |
| <mark class="confident"/>**PKCS #7 / P7B** | <mark class="confident"/>`.p7b` |<mark class="confident"/> Certificate/chain container, generally **without private keys**; encoding varies. |

<mark class="confident"/>**Note:** A `.crt` extension alone does **not** tell you whether the contents use DER or PEM encoding.

### Asymmetric key management

**Key lifecycle:** Choose approved, publicly scrutinized algorithms → generate unpredictable, adequately strong keys → protect private keys → securely back up/recover where appropriate → rotate/renew on policy or compromise → revoke and securely retire/destroy old keys.

- <mark class="confident"/>**Hardware Security Module (HSM):** Tamper-resistant hardware for generating, protecting, and using cryptographic keys; may also accelerate cryptographic operations. Enterprise and cloud HSMs are available.
- **Private key compromise:** Can enable impersonation and decryption depending on the algorithm and protocol. **Revoke and replace** the affected certificate/key; investigate exposure. Forward secrecy can protect older ephemeral sessions.
- **Key escrow / recovery:** Authorized storage/recovery of keys for business continuity. Apply **split knowledge** and **M-of-N control** (e.g., 3 of 8 approved custodians must cooperate) to prevent unilateral misuse.
- **Certificate renewal is not the same as revocation:** Expiration is a planned end of validity; **revocation** invalidates before expiry.

## 6. Hybrid Cryptography and Transport Layer Security (TLS)

**Hybrid cryptography** combines **asymmetric mechanisms for authentication/key agreement** with fast **symmetric encryption for bulk data**. An **ephemeral session key** is generated for temporary communication and discarded afterward.

**Example:** Browser ↔ website connection: validate the server certificate, agree on session secrets using authenticated key exchange, then encrypt application data symmetrically.

| Technology | Security meaning / example |
|---|---|
| **Secure Sockets Layer (SSL)** | Historical web-security protocol with serious vulnerabilities; **obsolete/insecure**. |
| **Transport Layer Security (TLS)** | Protocol securing data in transit, combining authentication, key establishment, and symmetric authenticated encryption. **TLS is a protocol, not an encryption algorithm**. |
| **TLS 1.2** | Older modern TLS version; security depends on **configuration/cipher suites**. |
| **TLS 1.3** | Newer TLS version with simplified authenticated handshake, improved security and performance, and **Authenticated Encryption with Associated Data (AEAD)** cipher suites. |
| <mark class="confident"/>**Cipher suite** | <mark class="confident"/>Specifies compatible cryptographic primitives for a TLS connection. In TLS 1.3, cipher suites identify the **AEAD symmetric algorithm and hash**, while key exchange is negotiated separately. |
| <mark class="confident"/>**Perfect Forward Secrecy (PFS)** | <mark class="confident"/>Compromise of a server's **long-term private key** should not decrypt previously recorded sessions when properly configured with ephemeral key agreement. |
| **Ephemeral Diffie–Hellman (DHE) / Elliptic Curve Diffie–Hellman Ephemeral (ECDHE)** | Temporary key agreement commonly used to provide PFS. |

**CISSP exam clue:** Fast bulk encryption + secure key agreement → **hybrid cryptography**; encrypted website channel → **TLS**; protects **past sessions** from later long-term key compromise → **PFS**.

## <mark class="confident"/> 7. Applied Cryptography

### Portable devices and data at rest

| Technology | What it protects |
|---|---|
| **Full-Disk Encryption (FDE)** | Encrypts an entire disk/volume to protect stored data if a laptop or drive is lost or stolen. |
| **BitLocker (Microsoft)** | Windows full-disk/volume encryption. |
| **FileVault (Apple)** | macOS disk encryption. |
| **Encrypting File System (EFS)** | Windows file/folder-level encryption; different from BitLocker. |
| **VeraCrypt** | Cross-platform tool for encrypted containers and volumes. |
| **Trusted Platform Module (TPM)** | Hardware-supported protection for keys and device/platform measurements; may protect FDE keys and bind unlocking to an expected device state. |

**Exam clue:** Stolen drive should remain unreadable when removed from the computer → **FDE + securely protected keys**, often with a **TPM**. Encryption does not necessarily protect files against an attacker who accesses an already **unlocked** system.


### Secure Email

| Approach | Explanation / Example |
|---|---|
| <mark class="confident"/>**Pretty Good Privacy (PGP) / OpenPGP** | <mark class="confident"/>Used to **encrypt and digitally sign emails and files**. It can use a **Web of Trust**, where users verify and trust each other's public keys instead of depending on a central Certificate Authority (CA). **Example:** Alice trusts Bob's public key because someone Alice already trusts has verified it. |
| <mark class="confident"/>**Secure/Multipurpose Internet Mail Extensions (S/MIME)** | <mark class="confident"/>Also used to **encrypt and digitally sign emails**, but relies on **digital certificates issued by trusted Certificate Authorities (CAs)** to verify identities. **Example:** A company uses CA-issued certificates to secure emails between employees in Microsoft Outlook. |

**Email Security Rules:**
- **Encryption → Confidentiality:** Only the intended recipient can read the email.
- **Digital Signature → Integrity, Authentication, Nonrepudiation:** Proves who signed the email and that its contents have not changed.
- **Encryption + Digital Signature → All four protections.**
- **Hash alone → Detects changes but does not prove the sender's identity.**

**CISSP Exam Clue:** Web of Trust → **PGP**; CA-issued X.509 certificates → **S/MIME**.


### Web privacy, steganography, and watermarking

| Concept | Explanation and example |
|---|---|
| **Tor (The Onion Router)** | Routes traffic through multiple relays with layered encryption to help conceal source identity. Provides anonymity properties but not unconditional protection from every tracking method. |
| **Steganography** | **Hides the existence of a message** inside another file, such as embedding secret bits in image pixels. Unlike encryption, its primary purpose is concealment. |
| **Least Significant Bit (LSB)** | Common steganography method: tiny changes to low-impact pixel bits can encode information with little visible change. |
| **Digital watermarking** | Embeds identifying/provenance information into media to help detect unauthorized copying or establish ownership. May use steganographic methods. |

<mark class="confident"/>**CISSP exam clue:** **Encryption hides meaning**; **steganography hides existence**; **watermarking helps prove ownership/trace copies**.

### Network encryption, Secure Shell, and Internet Protocol Security

| Approach | What gets protected / exam distinction |
|---|---|
| **Link encryption** | Encrypts traffic **between adjacent network devices or endpoints of a protected link**; generally decrypts/re-encrypts at intermediate link boundaries so traffic can be routed. Protects link-layer information as defined by the link mechanism. |
| **End-to-end encryption** | Protects data between final communicating endpoints, e.g., user/browser ↔ web server. Intermediate routers usually still need routable address information. |
| **Secure Shell (SSH) version 2** | Encrypted remote administration and secure file transfer, including **SSH File Transfer Protocol (SFTP)**. **SSH-1 is obsolete/insecure**. |
| **Internet Protocol Security (IPsec)** | Network-layer suite for protected Internet Protocol (IP) communications, widely used for **Virtual Private Networks (VPNs)**. |


#### <mark class="confident"/> IPsec Components and Modes

| Term | Explanation / Example |
|---|---|
| **Authentication Header (AH)** | Protects data from **unauthorized modification** and verifies the sender. Also prevents replay attacks, but **does not encrypt data**, so attackers may still read its contents. **Memory:** AH = Authentication and Integrity, NOT Confidentiality. |
| **Encapsulating Security Payload (ESP)** | **Encrypts data to keep it confidential** and can also provide integrity, authentication, and replay protection. **Example:** Protects sensitive information traveling through a Virtual Private Network (VPN). **Memory:** ESP = Encryption + Authentication. |
| **Transport Mode** | Protects the **data (payload) inside an Internet Protocol (IP) packet**, while keeping the original IP header visible for routing. Commonly used for **host-to-host communication**, such as two servers communicating securely. |
| **Tunnel Mode** | Protects the **entire original IP packet**, including its original header, and places it inside a new packet with a new outer IP header. Commonly used for **site-to-site VPNs**, such as connecting Hyderabad and Bangalore office networks securely over the internet. |
| **Security Association (SA)** | An agreement between two devices defining **how their IPsec communication is protected**, including encryption algorithms, keys, and security parameters. Each SA protects traffic in **one direction only**. **Example:** Two-way communication requires two SAs (one for sending and one for receiving). Using both AH and ESP in both directions can require four SAs. |

**CISSP Exam Clues:**
- **AH → Authentication + Integrity, no encryption.**
- **ESP → Encryption + Integrity/Authentication.**
- **Transport Mode → Protects payload; original IP header remains.**
- **Tunnel Mode → Protects entire original IP packet; adds new IP header.**
- **SA → One-way security agreement; two directions need two SAs.**


**CISSP exam clue:** **AH → authenticate, no encryption**; **ESP → encryption + integrity**; **transport → payload**; **tunnel → entire original IP packet**; **SA → one direction**.

## <mark class="confident"/> 8. Emerging Cryptographic Applications

| Application | Explanation and Example |
|---|---|
| **Blockchain** | A **shared digital record book** maintained by multiple computers instead of one central authority. Records are linked using cryptographic hashes, making unauthorized changes difficult and detectable. **Example:** Bitcoin records transactions across a distributed network. **Key Point:** Blockchain protects record integrity but does not guarantee that the original information is correct. |
| **Lightweight Cryptography** | Encryption techniques designed for devices with **limited battery power, memory, or processing capacity**. They provide security while consuming fewer resources. **Example:** Smartcards, Internet of Things (IoT) sensors, and battery-powered devices. |
| **Low-Latency Cryptography** | Encryption designed to **minimize the time needed to encrypt and decrypt data**, avoiding delays in communication. **Example:** High-speed network devices use dedicated encryption hardware to process traffic quickly. |
| **Homomorphic Encryption** | Allows computations to be performed **directly on encrypted data without decrypting it first**. The final encrypted result can be decrypted to obtain the correct answer. **Example:** A hospital sends encrypted patient data to a cloud service, which calculates statistics without seeing the actual patient information. |

**CISSP Exam Clues:**
- **Blockchain → Distributed, tamper-evident records.**
- **Lightweight Cryptography → Low-power, resource-limited devices.**
- **Low-Latency Cryptography → Fast encryption with minimal delay.**
- **Homomorphic Encryption → Calculate on encrypted data without decrypting it.**

## <mark class="confident"/> 9. Cryptographic Attacks and Defenses

| Attack | Simple Explanation | Example / CISSP Clue |
|---|---|---|
| **Brute-Force Attack** | The attacker **tries possible keys or passwords repeatedly** until finding the correct one. It does not depend on discovering a weakness in the encryption algorithm. | Trying every possible encryption key. **Defense:** Strong algorithms and sufficiently long keys. |
| **Ciphertext-Only Attack** | The attacker has **only encrypted messages**, without knowing the original messages or encryption keys. They analyze the ciphertext to discover the original information or key. | Capturing encrypted network traffic and trying to decrypt it. **Clue:** Only ciphertext available. |
| **Frequency Analysis** | The attacker **counts how frequently letters or patterns appear** in encrypted text. Classical ciphers may preserve recognizable language patterns, helping the attacker guess the original letters. | In English, E is a common letter. If X appears unusually frequently in a simple substitution cipher, X might represent E. **Clue:** Letter frequency patterns. |
| **Known-Plaintext Attack** | The attacker already knows **some original text and its corresponding encrypted version**. By comparing both, they attempt to discover the encryption key or weakness. | Knowing that an encrypted document begins with "CONFIDENTIAL" and having its ciphertext. **Clue:** Both original and encrypted text are known. |
| **Chosen-Plaintext Attack** | The attacker can **select the original message and obtain its encrypted version**. By encrypting carefully selected messages, they study how the algorithm transforms data. | Submitting "AAAA" and "BBBB" to an encryption service and comparing the outputs. **Clue:** Attacker chooses plaintext. |
| **Chosen-Ciphertext Attack** | The attacker can **submit selected encrypted messages to a decryption system** and observe the decrypted output or useful error responses. This helps them discover weaknesses or recover information. | Sending specially modified encrypted messages to a server and analyzing its responses. **Clue:** Attacker chooses ciphertext for decryption. |
| **Analytic Attack** | The attacker **studies the mathematical design of an encryption algorithm** to find weaknesses that make breaking it easier than trying every key. | Discovering a mathematical shortcut that reduces the work needed to recover an encryption key. **Clue:** Mathematical weakness in algorithm design. |
| **Implementation Attack** | The encryption algorithm may be secure, but the attacker exploits **mistakes in how software or hardware implements it**. | An application incorrectly handles encryption errors, allowing information to leak. **Clue:** Secure algorithm, insecure implementation. |
| **Statistical Attack** | The attacker looks for **predictable patterns in cryptographic values**, such as poorly generated random numbers, to guess keys or other secrets. | A weak random number generator repeatedly produces predictable encryption keys. **Clue:** Weak randomness or statistical patterns. |
| **Side-Channel Attack** | Instead of breaking encryption mathematically, the attacker observes **physical or operational information leaked by the device** while encryption runs. | Measuring a smartcard's power consumption to infer its secret key. **Clue:** Power usage, electromagnetic emissions, or cache behavior. |
| **Timing Attack** | A specific side-channel attack where the attacker measures **how long an operation takes** to discover secret information. | A password comparison takes slightly longer when more initial characters match. **Clue:** Processing-time differences. |
| **Fault-Injection Attack** | The attacker **deliberately causes a device to malfunction** so it behaves incorrectly and may reveal protected information. | Manipulating a smartcard's voltage during encryption to cause errors that help recover its key. **Clue:** Intentionally induced hardware/software faults. |
| **Man-in-the-Middle (MITM) Attack** | The attacker secretly positions themselves **between two communicating parties**, pretending to be each party to the other. They may intercept, read, or modify communications. | Alice thinks she is communicating securely with Bob, but an attacker establishes separate connections with both. **Clue:** Intercepting and impersonating communicating parties. |
| **Meet-in-the-Middle Attack** | An attack against **multiple layers of encryption**. The attacker encrypts known plaintext using possible first keys and decrypts known ciphertext using possible second keys, looking for matching intermediate results. | Breaking Double Data Encryption Standard (2DES) more efficiently than trying every possible pair of keys. **Clue:** Matching encryption and decryption results in the middle. |
| **Birthday / Collision Attack** | The attacker tries to find **two different messages that produce the same hash value**, exploiting the mathematical birthday paradox. | Creating two different documents with identical hashes so that a signature on one might be misused for the other. **Clue:** Different inputs, same hash. |
| **Replay Attack** | The attacker **captures a valid authentication message and sends it again later** to trick a system into accepting it. The attacker may not need to decrypt the message. | Recording a valid authentication request and retransmitting it to gain access. **Defense:** Nonces, timestamps, expiration, and challenge-response authentication. |
| **Rainbow-Table Attack** | The attacker uses a **precomputed database of password hashes** to quickly look up possible passwords instead of calculating every hash during the attack. | A stolen password hash matches a hash in a rainbow table, revealing the likely password. **Defense:** Unique salts and slow password-hashing algorithms. |

### Important CISSP Distinctions

| Comparison | Key Difference |
|---|---|
| **Known Plaintext vs. Chosen Plaintext** | Known = Attacker already has matching original and encrypted text. Chosen = Attacker selects the original text to be encrypted. |
| **Chosen Plaintext vs. Chosen Ciphertext** | Chosen Plaintext = Attacker controls encryption input. Chosen Ciphertext = Attacker controls decryption input. |
| **Man-in-the-Middle vs. Meet-in-the-Middle** | Man = Intercepts communication between people/systems. Meet = Mathematical attack against multiple encryption layers. |
| **Analytic vs. Implementation** | Analytic = Weakness in algorithm design. Implementation = Weakness in how the algorithm is implemented. |
| **Side-Channel vs. Timing** | Side-Channel = Information leaks through physical or operational behavior. Timing = Specific side-channel using execution time. |
| **Frequency Analysis vs. Statistical Attack** | Frequency Analysis = Examines character patterns in ciphertext. Statistical Attack = Broader exploitation of statistical weaknesses, including weak randomness. |
| **Birthday vs. Rainbow Table** | Birthday = Finds different inputs with the same hash. Rainbow Table = Uses precomputed hashes to guess passwords. |

**Memory:** Brute Force = Guess everything; Known Plaintext = Already know; Chosen Plaintext = Choose what to encrypt; Chosen Ciphertext = Choose what to decrypt; Replay = Reuse valid message; Birthday = Same hash; Rainbow Table = Precomputed hashes.


### Password hashing and defenses

- **Salt:** Unique random value combined with each password before hashing; the salt can be stored alongside its hash. Two users with the same password should have **different stored hashes** when their salts differ. **Prevents direct use of precomputed rainbow tables**, but is not sufficient by itself against fast offline guessing.
- **Key stretching / slow password hashing:** Makes each password guess costly. The chapter names **Password-Based Key Derivation Function 2 (PBKDF2)**, **bcrypt**, and **scrypt**.
- **Nonce (number used once):** Fresh, one-time value to prevent reuse/replay in security protocols; unlike a password salt, it addresses **protocol freshness**.
- **CISSP clue:** **Rainbow tables → salts**; **offline brute force → slow password hashing/key stretching**; **recorded authentication reused → nonce/timestamp/challenge-response**.

## 11. Accuracy Notes — Externally Verified Clarifications to the Supplied Chapter

The uploaded chapter includes some simplified or outdated statements. These points are **clarifications from standards**, not direct quotations from the supplied text:

1. **TLS 1.3 key exchange:** The chapter describes encrypting and transporting a session key with the server's RSA public key. **Actual TLS 1.3 does not use RSA key transport.** It uses authenticated (typically ephemeral Diffie–Hellman) key establishment or supported pre-shared-key mechanisms, then derives traffic keys. **Reference:** [Internet Engineering Task Force (IETF) RFC 8446](https://www.rfc-editor.org/rfc/rfc8446).
2. **TLS 1.3 cipher suites:** The chapter gives an example of **AES-CBC** as though it were a TLS 1.3 suite. **Actual TLS 1.3 suites use Authenticated Encryption with Associated Data (AEAD)**, such as **AES-GCM**, not CBC mode. **Reference:** [IETF RFC 8446](https://www.rfc-editor.org/rfc/rfc8446).
3. **Digital Signature Standard hash functions:** The chapter implies FIPS 186-5 requires **only SHA-3**. The standard permits appropriate approved hashing functions from **FIPS 180 (SHA family)** and **FIPS 202 (SHA-3)**. **Reference:** [NIST FIPS 186-5](https://csrc.nist.gov/pubs/fips/186-5/final).
4. **Wildcard certificates:** The chapter says `*.example.org` covers `example.org`. **A normal single-label wildcard does not cover the apex domain** unless that domain is listed separately. **Reference:** [IETF RFC 6125](https://www.rfc-editor.org/rfc/rfc6125).
5. **Post-quantum progress:** The chapter presents quantum-resistant cryptography as largely future research. **NIST standardized initial post-quantum algorithms in August 2024**, including **Module-Lattice-Based Key-Encapsulation Mechanism (ML-KEM)**, **Module-Lattice-Based Digital Signature Algorithm (ML-DSA)**, and **Stateless Hash-Based Digital Signature Algorithm (SLH-DSA)**. **Reference:** [NIST Post-Quantum Cryptography project](https://csrc.nist.gov/projects/post-quantum-cryptography).
