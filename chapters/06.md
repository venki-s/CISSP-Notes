# CISSP Chapter 6 — Cryptography and Symmetric Key Algorithms

**Domain 3: Security Architecture and Engineering**  
**Study approach:** One unified revision guide. Focus on purpose, differences, security weaknesses, and exam clues rather than detailed cipher calculations.

## 1. Why Cryptography Is Used

| Security goal | Meaning and exam example |
|---|---|
| **Confidentiality** | Prevent unauthorized disclosure. **Example:** Encrypt a stolen laptop's files so they cannot be read. |
| **Integrity** | Detect unauthorized or accidental data changes. **Example:** Compare a document's cryptographic hash before and after transfer. |
| **Authentication** | Verify a claimed identity or message origin. **Example:** A challenge–response protocol demonstrates possession of a secret. |
| <mark class="confident"/> **Nonrepudiation** | <mark class="confident"/> Provide evidence that a sender cannot credibly deny having signed/sent a message. <mark class="confident"/>**Example:** A digital signature created with the sender's private key and verified using the public key. |

<mark class="confident"/> **Remember:** Encryption alone primarily provides **confidentiality**. A hash can help **detect changes**, but does not by itself prove who created the data. **Digital signatures** support integrity, origin authentication, and nonrepudiation; ordinary **shared-secret symmetric encryption cannot provide nonrepudiation**, because both parties know the key.

### Three states of data

| State | Where data exists | Main consideration |
|---|---|---|
| **At rest** | Disks, backups, cloud storage | Protect against media theft and unauthorized storage access. |
| **In transit / in motion** | Between systems or across a network | Protect against interception or tampering in communications. |
| **In use** | Active memory / processing | Prevent unauthorized process access; encryption at rest does not automatically protect exposed plaintext in memory. |

## 2. Cryptography Vocabulary and Principles

| Term | Short definition |
|---|---|
| **Plaintext** | Readable original information, before encryption. |
| **Ciphertext** | Scrambled output of encryption; requires the correct decryption process/key to restore readable content. |
| <mark class="confident"/> **Cipher / algorithm** | <mark class="confident"/> Mathematical rules used to transform plaintext and ciphertext. |
| **Key** | Secret or private value that determines a specific encryption/decryption outcome. |
| <mark class="confident"/> **Key Space** | <mark class="confident"/>The total number of possible encryption keys for a given key length. Each bit can be 0 or 1, so an **n-bit key has 2^n combinations** (e.g., 3-bit) |
| <mark class="confident"/> **Cryptography** | <mark class="confident"/>Design/use of techniques to protect information. |
| **Cryptanalysis** | Study of techniques for breaking cryptographic protections. |
| <mark class="confident"/> **Cryptology** | <mark class="confident"/> Cryptography plus cryptanalysis. |
| **Cryptosystem** | Implementation of algorithms, keys, procedures, and supporting components. |
| <mark class="confident"/> **Work factor / work function** | <mark class="confident"/> Time, effort, or cost required to defeat a cryptosystem; must exceed the period for which the information needs protection. |

- <mark class="confident"/> **Kerckhoffs's Principle:** A cryptosystem must remain secure even if the **algorithm is publicly known**; secrecy rests on the **key**, not on hiding the algorithm. **Exam clue:** Relying on a secret algorithm alone is *security through obscurity*.
- **Strong key management matters as much as algorithm selection:** Protect secret/private keys, use sufficient length and randomness, and replace compromised or obsolete keys.
- <mark class="confident"/> **FIPS 140-3 (Federal Information Processing Standard 140-3):** Defines security requirements for cryptographic modules (hardware, software, or firmware), covering areas such as key management, access controls, and physical security. It has **four security levels (1–4)**, with Level 4 providing the highest protection. **Example:** Using AES-256 does not automatically make a product FIPS 140-3 compliant; its cryptographic module must be independently tested and validated through the **Cryptographic Module Validation Program (CMVP)**. **CISSP Clue:** FIPS 140-3 evaluates cryptographic **modules**, not just encryption algorithms.


## 3. Essential Cryptographic Mathematics — Only the Exam Basics

| Operation | Rule | Example |
|---|---|---|
| **AND** | 1 only when **both** input bits are 1. | 1 AND 0 = 0 |
| **OR** | 1 when **at least one** input bit is 1. | 1 OR 0 = 1 |
| **NOT** | Reverses a bit. | NOT 1 = 0 |
| **Exclusive OR (XOR)** | 1 when bits are **different**; 0 when they are equal. | 1 XOR 0 = 1; 1 XOR 1 = 0 |
| **Modulo (mod)** | Returns the **remainder** after division. | 10 mod 3 = 1 |

- <mark class="confident"/> **XOR is reversible with the same value:** If `C = P XOR K`, then `P = C XOR K`. It is widely used in ciphers and the one-time pad.
- <mark class="confident"/> **One-way function:** Easy to compute in one direction but computationally impractical to reverse. Used as a foundation for cryptographic protections.
- <mark class="confident"/> **Nonce (number used once):** A value used **once within the relevant context** to make an operation unique and help prevent reuse/replay problems. Reusing a nonce where uniqueness is required may destroy security.
- <mark class="confident"/> **Initialization Vector (IV):** An additional starting value for certain cipher modes so identical plaintext encrypted under a key need not produce identical ciphertext. **IV requirements depend on the mode** (for example, uniqueness and/or unpredictability).
- <mark class="confident"/> **Zero-Knowledge Proof (ZKP):** Prove knowledge of a secret **without revealing the secret**. **Example:** Demonstrating that you know a password without transmitting the password itself.

## 4. Classical Ciphers and One-Time Pads

| Concept | What to remember |
|---|---|
| <mark class="confident"/> **Code versus cipher** | <mark class="confident"/> A **code** replaces words or phrases (e.g., “10-4”); a **cipher** transforms letters, bits, or blocks to conceal meaning. |
| <mark class="confident"/> **Transposition cipher** | <mark class="confident"/> **Rearranges** character positions without changing the characters themselves. **Example:** `APPLE` → `ELPPA` by reversing the text. |
| <mark class="confident"/> **Substitution cipher** | <mark class="confident"/>**Replaces** characters with other characters. **Example:** Caesar shift by three positions, `A` → `D`. |
| <mark class="confident"/>**Monoalphabetic substitution** | <mark class="confident"/>Uses one consistent substitution mapping; vulnerable to **frequency analysis**. |
| <mark class="confident"/>**Polyalphabetic substitution** | <mark class="confident"/>Uses multiple mappings; the **Vigenère cipher** uses a repeated key and is vulnerable to **period analysis**. |
| <mark class="confident"/>**Running-key / book cipher** | <mark class="confident"/>Uses a long key taken from a book or other text; **not equivalent to a truly random one-time pad**. |

### One-Time Pad (OTP) / Vernam Cipher

A **one-time pad (OTP)** combines plaintext with a key using an operation such as Exclusive OR (XOR). Properly implemented, it offers **perfect secrecy**, but *all* the following conditions must hold:

1. The key is **truly random**.
2. The key is **at least as long as the message**.
3. The key is **kept secret** and protected from disclosure.
4. **Every key is used only once**; it must never be reused.

<mark class="confident"/>**Exam clue:** A long key **does not automatically** make a cipher a one-time pad. Reusing a pad or using predictable key material removes its perfect-secrecy guarantee. The **VENONA** example in the chapter illustrates the danger of weak/non-random pad material.

### Block versus stream, confusion versus diffusion

| Pair | Distinction |
|---|---|
| **Block cipher** | Encrypts fixed-size blocks of data, such as 128-bit blocks in Advanced Encryption Standard (AES). |
| **Stream cipher** | Processes a stream of bits/characters progressively, often suitable for continuous data. |
| <mark class="confident"/>**Confusion** | <mark class="confident"/>Obscures the relationship between the **encryption key, plaintext, and ciphertext**, making it difficult to determine the key by analyzing encrypted data. Primarily achieved through **substitution**, where input values are replaced with other values using complex rules. **Example:** Replacing plaintext letters or bits with different values based on the encryption key. |
| <mark class="confident"/>**Diffusion** | <mark class="confident"/>Spreads the influence of each plaintext bit across **multiple ciphertext bits**, making it difficult to identify patterns in the original message. Traditionally associated with **transposition/permutation**, which rearranges the positions of bits. **Example:** In modern encryption, changing a single plaintext bit can change many ciphertext bits after multiple encryption rounds (avalanche effect). |

<mark class="confident"/> **Memory:**
- <mark class="confident"/>**Confusion → Substitution → Hides the relationship with the key.**
- <mark class="confident"/>**Diffusion → Transposition → Spreads plaintext influence across ciphertext.**
- <mark class="confident"/>**CISSP Exam Clue:** Confusion hides relationships; diffusion hides statistical patterns.


## 5. Symmetric versus Asymmetric Cryptography

| Feature | Symmetric key cryptography | Asymmetric / public key cryptography |
|---|---|---|
| **Keys** | One **shared secret** for encryption and decryption. | Each user has a **public/private key pair**. |
| **Performance** | **Fast**; appropriate for bulk data encryption. | **Slower**; appropriate for key establishment and digital signatures. |
| **Key distribution** | Shared secret must be transferred/established securely. | Public keys can be distributed; private keys remain secret. |
| **Scalability** | One unique key for every communicating pair becomes difficult to manage. | Easier to scale; one key pair per participant. |
| **Nonrepudiation** | **No**, because all holders of the shared key can create the same cryptographic outputs. | **Yes**, with a properly implemented and controlled digital signature. |
| **Typical application** | Bulk data protection. | Establishing secure sessions, certificates, signatures. |

- <mark class="confident"/> **Pairwise symmetric key count:** For *n* users, `n(n − 1) / 2` distinct pairwise shared keys are needed. **Example:** 10 users → 45 shared keys.
- <mark class="confident"/> **Asymmetric key count:** For *n* users, there are generally **2n keys** (one public and one private per user). **Example:** 10 users → 20 keys.
- **Hybrid cryptography:** Uses asymmetric techniques to **establish or protect a shared secret**, then uses fast symmetric encryption for session data. **Example:** Transport Layer Security (TLS) commonly uses this broad approach.
- <mark class="confident"/> **Ephemeral/session key:** Short-lived key used for a session rather than indefinitely; limits how long a single key is exposed.
- **Hash function:** Produces a fixed-length **message digest/fingerprint**; it is **not encryption** and cannot be “decrypted.” A **collision** occurs when two different inputs produce the same digest. Hashes support integrity checking and digital signatures when combined with additional mechanisms.

**Exam trap:** A symmetric **shared secret** is not the same thing as an asymmetric **private key**. The latter belongs to one key pair and should not be shared.

## <mark class="confident"/>6. Block Cipher Modes of Operation — High Priority

| Mode | How it works / CISSP distinction | Main concern or advantage |
|---|---|---|
| **Electronic Codebook (ECB)** | Independently encrypts each block; **identical plaintext blocks → identical ciphertext blocks** under the same key. | **Leaks patterns**; unsuitable for general bulk encryption. |
| **Cipher Block Chaining (CBC)** | Combines each plaintext block with the **previous ciphertext block** before encryption; uses an **Initialization Vector (IV)** for the first block. | Chaining hides repeated patterns; a ciphertext error affects the current and next plaintext blocks. |
| **Cipher Feedback (CFB)** | Uses feedback from prior **ciphertext** to produce a stream-like operation; uses an IV. | Feedback/chaining is important; errors may propagate temporarily. |
| **Output Feedback (OFB)** | Generates a keystream from the **previous output/seed**, not from the ciphertext. | Transmission bit errors **do not propagate** to later blocks. |
| **Counter (CTR)** | Encrypts successive **counter values** to generate a keystream. | Supports **parallel processing**; errors do not propagate. **Never repeat the same counter/nonce sequence with the same key.** |
| **Galois/Counter Mode (GCM)** | Adds an **authentication tag** to counter-based encryption. | **Authenticated encryption:** confidentiality **and** integrity/authenticity. |
| **Counter with Cipher Block Chaining Message Authentication Code (CCM)** | Uses **CTR** for encryption plus **Cipher Block Chaining Message Authentication Code (CBC-MAC)** for authentication. | **Authenticated encryption:** confidentiality **and** integrity/authenticity; needs proper nonce management. |

**Most important exam distinction:** **ECB, CBC, CFB, OFB, and CTR** are primarily confidentiality modes; **GCM and CCM** add message authentication. An ordinary encrypted message is **not automatically tamper-resistant**. For new designs, choose a suitable authenticated-encryption mode rather than ECB.

**Memory shortcuts:** `ECB = pattern leakage`; `CBC = chaining`; `CFB = ciphertext feedback`; `OFB = output feedback`; `CTR = counter / parallel`; `GCM and CCM = encryption + authentication`.

## <mark class="confident"/>7. Symmetric Algorithms — What to Memorize

### Important algorithms

| Algorithm | Block size | Key size | CISSP importance / security status |
|---|---|---|---|
| **Advanced Encryption Standard (AES)** | **128 bits** | **128, 192, or 256 bits** | Modern standard; based on **Rijndael**. **10 / 12 / 14 rounds** respectively. |
| **Data Encryption Standard (DES)** | **64 bits** | **56 effective bits** | Obsolete/insecure against brute force; **16 rounds**. A 64-bit DES key representation includes **8 parity bits**. |
| **Triple Data Encryption Standard (3DES / Triple DES)** | **64 bits** | Two- or three-key variants; often described as **112 or 168 nominal key bits** | Repeats DES three times; **deprecated / unsuitable for new protection**. Three-key variants have approximately **112-bit effective security** because of attacks. |
| **International Data Encryption Algorithm (IDEA)** | **64 bits** | **128 bits** | Historical symmetric block cipher; associated with older Pretty Good Privacy (PGP) implementations. |
| **Blowfish** | **64 bits** | **32–448 bits** | Older fast block cipher with variable key length; legacy rather than a modern first choice. |
| **Rivest Cipher 4 (RC4)** | **Stream cipher** | Variable (guide: **40–2,048 bits**) | **Insecure**; historically used in Wired Equivalent Privacy (WEP), Wi-Fi Protected Access (WPA), Secure Sockets Layer (SSL), and older Transport Layer Security (TLS). |
| **Rivest Cipher 5 (RC5)** | **32, 64, or 128 bits** | Variable | Historical configurable **block cipher**, *not* a revision of the RC4 stream cipher. |
| **Rivest Cipher 6 (RC6)** | **128 bits** | **128, 192, or 256 bits** | Block cipher; **AES competition finalist**, not the selected standard. |
| **SKIPJACK** | **64 bits** | **80 bits** | Legacy U.S. government cipher associated with the **Clipper chip** and **key escrow**. |
| **CAST-128 / CAST-256** | **64 / 128 bits** | Variable (CAST-128 up to 128; CAST-256 up to 256) | Historical block ciphers; CAST-256 was an AES candidate. |

### <mark class="confident"/>AES and DES must-know facts

- **AES (Advanced Encryption Standard):** Always **128-bit block size**, regardless of key length. Key lengths **128 / 192 / 256 bits** correspond to **10 / 12 / 14 rounds**. **Exam clue:** Preferred modern symmetric algorithm → **AES**.
- **Rijndael versus AES:** Rijndael supports multiple block sizes; the **AES standard restricts the block size to 128 bits**.
- **DES (Data Encryption Standard):** **64-bit blocks, 56-bit effective key, 16 rounds**; vulnerable to brute-force attacks.
- **3DES (Triple Data Encryption Standard):** Stronger than single DES but old and significantly less suitable than AES; its **64-bit block size** is also a limitation. **Do not select it for new systems.**
- **Double DES:** Vulnerable to a **meet-in-the-middle attack**, which undermines its expected security gain.

**Low-priority detail:** For exams, recognize legacy algorithms and their broad properties, but devote most recall effort to **AES, DES, 3DES, RC4, and key-management concerns** rather than memorizing every historical cipher's exact key range.

## 8. Key Creation, Distribution, Storage, Recovery, and Destruction

### Secure key distribution

| Method | Key idea / concern |
|---|---|
| **Offline / out-of-band distribution** | Physically deliver the secret key; workable but subject to interception, loss, and logistical difficulties. |
| **Public-key-assisted exchange** | Use asymmetric cryptography to establish/protect a symmetric secret, then encrypt bulk traffic symmetrically. |
| <mark class="confident"/> **Diffie–Hellman key exchange** | <mark class="confident"/> Allows parties to establish a shared secret without previously sharing the secret; examined further in Chapter 7. |

### Key-management principles

1. **Generate:** Use secure randomness and sufficiently strong, approved algorithms/key lengths.
2. **Distribute:** Prevent unauthorized disclosure during key establishment or transfer.
3. **Store:** Protect keys from theft and unauthorized use; limit access, ideally separating key material from the ciphertext it protects.
4. **Use and rotate:** Limit usage, rekey when required by policy or after compromise; revoke/replace keys when participants lose authorization.
5. **Recover:** Maintain approved recovery/escrow where needed, with strong authorization and oversight.
6. **Retire and destroy:** Securely delete or destroy obsolete keys and related backup copies; consider whether encrypted data must remain recoverable.

### Key storage and recovery terms

| Term | Explanation and exam clue |
|---|---|
| **Software-based key storage** | Stores keys in software/files, sometimes encrypted; convenient but may be exposed if the host is compromised. |
| **Hardware Security Module (HSM)** | Dedicated hardware for protected key storage and cryptographic operations; stronger key isolation than ordinary software storage. |
| <mark class="confident"/> **Cloud HSM / cloud key management** | <mark class="confident"/>Cloud-hosted implementation of protected key-management capabilities; provider and customer responsibilities must be clear. |
| <mark class="confident"/> **Key escrow** | <mark class="confident"/>A trusted recovery mechanism retains protected access to keys for authorized future recovery. **Example:** An employee leaves and the organization needs to recover encrypted records. |
| <mark class="confident"/>**Recovery agent (RA)** | <mark class="confident"/>An authorized individual or role who can recover escrowed keys; highly privileged and must be monitored. |
| **Split knowledge** | Divide sensitive key material or recovery capability so **no one individual** has the complete secret. |
| <mark class="confident"/>**M-of-N control** | <mark class="confident"/>At least **M of N authorized people** must cooperate for key recovery or another sensitive act. **Example:** Any 3 of 8 designated recovery agents must approve a recovery. |

**Exam traps:**
- <mark class="confident"/>**Escrow** is *storing/recovering a key*; **split knowledge** is *dividing the secret*; **M-of-N** is *requiring a threshold number of people*.
- **Key loss** may make encrypted data permanently inaccessible unless a secure recovery arrangement exists.
- <mark class="confident"/>**Symmetric group membership change:** A departing member may know old group keys, so **rekey** to protect future communications.
- <mark class="confident"/>**A strong algorithm is not enough** when keys are weak, shared improperly, stolen, or reused in violation of a cipher-mode requirement.

## 9. Cryptographic Life Cycle and Governance

Cryptographic strength changes over time because computing power and cryptanalysis improve. Choose algorithms and key sizes according to **data classification, required confidentiality lifetime, regulatory needs, and anticipated attacks**; review and replace algorithms before they become obsolete.

- Define an **approved algorithms and protocols** list, including **Advanced Encryption Standard (AES)** and permitted **Transport Layer Security (TLS)** configurations.
- Establish **minimum key lengths**, rotation/revocation/recovery procedures, secure storage, and disposal requirements.
- <mark class="confident"/>Monitor for deprecations, new attacks, and advances including **quantum computing**; migrate before sensitive long-lived data becomes vulnerable.
- <mark class="confident"/>Use risk-based decisions: Protect data for **as long as it remains valuable**, not merely until a short-lived session ends.

## 10. Rapid CISSP Exam Recall

| Scenario / wording in a question | Think of |
|---|---|
| Same key encrypts and decrypts, very fast, bulk data | **Symmetric cryptography** |
| Public/private key pair, digital signature, nonrepudiation | **Asymmetric cryptography** |
| Establish a secure connection with public-key techniques, then encrypt data quickly | **Hybrid cryptography** |
| Prove knowledge of a password without revealing it | **Zero-Knowledge Proof (ZKP)** |
| Shared key cannot establish which party sent a message | **No symmetric nonrepudiation** |
| Preserve security even if algorithm details become public | **Kerckhoffs's Principle** |
| Guessing keys becomes harder as key length grows | **Key space / work factor** |
| One-time pad key is reused, predictable, or shorter than message | **Perfect secrecy lost** |
| Same plaintext blocks produce matching ciphertext patterns | **Electronic Codebook (ECB)** |
| Each block depends on previous ciphertext block | **Cipher Block Chaining (CBC)** |
| Parallelizable counter-based encryption | **Counter (CTR)** |
| Encryption plus authenticity/integrity tag | **Galois/Counter Mode (GCM)** or **Counter with Cipher Block Chaining Message Authentication Code (CCM)** |
| 128-bit block, keys 128/192/256, rounds 10/12/14 | **Advanced Encryption Standard (AES)** |
| 64-bit block, 56-bit effective key, 16 rounds | **Data Encryption Standard (DES)** |
| Old stream cipher associated with WEP/SSL | **Rivest Cipher 4 (RC4)** |
| Several key custodians required for key recovery | **Split knowledge / M-of-N control** |
| Strong algorithm but keys stored insecurely | **Key-management failure** |
