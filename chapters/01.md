
# Chapter 1 — Security Governance Through Principles and Policies

**CISSP Domains:** 1 — Security and Risk Management; 3 — Security Architecture and Engineering

## 1. Fundamental Security Concepts

- Information security is a **business management responsibility**, not merely an IT responsibility.
- Security must align with organizational mission, goals, and business strategy.
- Security controls should be risk-based, cost-effective, legally defensible, and continuously evaluated.
- No system can be completely secure; security requires continuous improvement.

### Five Pillars of Information Security

| Pillar | Objective | Typical Controls |
|---|---|---|
| Confidentiality | Prevent unauthorized disclosure | Encryption, access controls, classification |
| Integrity | Prevent unauthorized/improper modification | Hashing, access controls, validation |
| Availability | Ensure timely access for authorized users | Redundancy, backups, fault tolerance |
| Authenticity | Verify genuine identity or origin | Authentication, digital signatures |
| Nonrepudiation | Prevent credible denial of an action | Digital signatures, audit trails |

### CIA vs. DAD Triads

| CIA Security Goal | DAD Violation |
|---|---|
| Confidentiality | Disclosure |
| Integrity | Alteration |
| Availability | Destruction / Denial of Service |

### Important Distinctions

- **Confidentiality:** Protects against unauthorized disclosure, whether intentional or accidental.
- **Integrity:** Protects accuracy, completeness, and consistency; includes preventing mistakes by authorized users.
- **Availability:** Includes timely access, adequate performance, and resilience against interruptions.
- **Authenticity:** Establishes that information or an entity is genuine and originates from the claimed source.
- **Nonrepudiation:** Provides evidence linking an entity to an action or transaction.
- **Security Through Obscurity:** Concealing the existence of a weakness is not an adequate security control.
- **Overprotection:** Excessive confidentiality or integrity restrictions may negatively affect availability.

## 2. Identification, Authentication, Authorization, Auditing, Accounting

**AAA = Authentication, Authorization, Accounting**

The complete accountability process also includes identification and auditing.

| Concept | Meaning |
|---|---|
| Identification | Claiming an identity |
| Authentication | Proving the claimed identity |
| Authorization | Determining permitted actions/resources |
| Auditing | Recording actions and security events |
| Accounting | Reviewing activities and establishing accountability |

### Important

- Authentication does not imply authorization.
- Auditing creates the record needed to reconstruct activity.
- Monitoring observes activity; auditing records it.
- Strong identification, authentication, and audit trails support accountability.
- Nonrepudiation requires reliable evidence linking an action to an entity.

## 3. Security Protection Mechanisms

### Defense in Depth
- Multiple independent security controls arranged in layers.
- Failure of one control should not compromise the entire system.
- **Defense Diversity:** Using different technologies/vendors reduces common-mode failures.

### Abstraction
- Groups similar objects, users, or functions for simplified security administration.
- Supports role-based permission management.

### Data Hiding
- Prevents unauthorized subjects from discovering or accessing protected information.
- Unlike security through obscurity, data hiding enforces actual access restrictions.

### Security Boundaries
- Separate environments with different trust or security requirements.
- Information crossing boundaries requires appropriate security controls.
- Boundaries may be physical, logical, or based on data classifications.

## 4. Security Governance

### Core Principles

- Security governance defines, directs, evaluates, and monitors organizational security.
- Senior management/board establishes security direction and accountability.
- Security responsibilities may be delegated, but ultimate accountability remains with senior management.
- A **top-down approach** is preferred.

### Top-Down Security Management

1. Senior management approves security policies and direction.
2. Middle management develops standards, procedures, and implementation plans.
3. Security professionals implement and maintain security controls.
4. Users comply with established requirements.
5. Auditors independently evaluate compliance and effectiveness.

### Security Roles

| Role | Primary Responsibility |
|---|---|
| Senior Management | Ultimate security accountability; approves security policy |
| CISO / Security Leadership | Directs and coordinates the information security function |
| Security Professional | Develops and implements controls under management direction |
| Asset Owner | Determines classification and protection requirements |
| Custodian | Implements protection, storage, backups, and maintenance |
| User | Follows policies and least-privilege requirements |
| Auditor | Independently evaluates compliance and control effectiveness |

### Key Distinctions

- **Asset Owner:** Decides classification and protection requirements.
- **Custodian:** Implements the owner's requirements.
- **Senior Management:** Ultimately accountable for organizational security.
- **CIO:** Focuses on effective business use of information.
- **CTO:** Focuses on technology supporting business operations.
- Security performance must be measurable through relevant metrics.

## 5. Security Management Planning

| Plan | Time Horizon | Purpose |
|---|---|---|
| Strategic | Long-term (~5 years) | Mission, vision, overall security goals |
| Tactical | Medium-term (~1 year) | Projects, budgets, resources, milestones |
| Operational | Short-term (monthly/quarterly) | Detailed activities, procedures, assignments |

### Important

- Strategic plans define **what the organization wants to achieve**.
- Tactical plans define **how strategic goals will be organized and accomplished**.
- Operational plans define **specific execution activities**.
- Senior management approval and ongoing support are essential.

## 6. Security Control Frameworks

| Framework | CISSP-Relevant Purpose |
|---|---|
| ISO/IEC 27000 Family | International information security management standards |
| NIST SP 800-53 | Security and privacy controls |
| NIST RMF | Risk management framework |
| NIST CSF | Framework for managing cybersecurity risk |
| COBIT | Governance and management of enterprise IT |
| SABSA | Business-driven, risk-focused security architecture |
| PCI DSS | Contractual security requirements for payment card data |
| FedRAMP | Security assessment, authorization, and continuous monitoring for US federal cloud services |
| ITIL | IT service management best practices |

### COBIT — Six Governance Principles

1. Provide Stakeholder Value.
2. Holistic Approach.
3. Dynamic Governance System.
4. Governance Distinct from Management.
5. Tailored to Enterprise Needs.
6. End-to-End Governance System.

### Framework Distinctions

- **COBIT:** Governance, business alignment, and IT control objectives.
- **SABSA:** Business-driven enterprise security architecture.
- **ISO/IEC 27000:** Information security management.
- **NIST SP 800-53:** Catalogue of security and privacy controls.
- **PCI DSS:** Payment card security; primarily contractual obligations.
- **FedRAMP:** US government cloud security authorization and monitoring.
- **CIS Benchmarks:** Secure configuration guidance, not a broad governance framework.

## 7. Due Diligence vs. Due Care

| Concept | Meaning |
|---|---|
| Due Diligence | Identify risks, establish appropriate security plans, and verify effectiveness |
| Due Care | Take reasonable actions to implement and maintain protection |
| Negligence | Failure to exercise reasonable care under applicable obligations |

### Important

- **Due Diligence:** Knowing, planning, assessing, and overseeing what must be done.
- **Due Care:** Actually implementing and maintaining required controls.
- Due diligence is continuous; controls and plans must be reassessed as conditions change.
- Senior management must demonstrate both to reduce negligence and liability risks.

## 8. Security Documentation Hierarchy

| Document | Purpose | Mandatory? |
|---|---|---|
| Policy | High-level security objectives and requirements | Yes |
| Standard | Specific, uniform security requirements | Yes |
| Baseline | Minimum acceptable security configuration | Yes |
| Procedure | Step-by-step implementation instructions | Required where prescribed |
| Guideline | Recommended implementation practices | No |

### Policy Types

- **Organizational Policy:** Organization-wide security requirements.
- **Issue-Specific Policy:** Requirements for a particular issue, service, or activity.
- **System-Specific Policy:** Requirements for individual systems or system categories.

### Key Distinctions

- **Policy:** What must be achieved and why.
- **Standard:** Specific requirements that must be followed.
- **Baseline:** Minimum acceptable security level.
- **Procedure:** Exact steps to perform an activity.
- **Guideline:** Optional recommendations and flexibility.

## 9. Organizational and Third-Party Governance

### Mergers and Acquisitions
- Assess acquired assets, systems, software, vendors, and inherited vulnerabilities.
- Consider confidentiality, availability, regulatory, and integration risks.
- Evaluate total cost of ownership, including security remediation.

### Divestitures
- Revoke access for departing employees.
- Conduct exit interviews and reinforce continuing confidentiality obligations.
- Securely sanitize, transfer, or destroy sensitive assets according to requirements.

### Third-Party Governance
- Conduct vendor risk assessments before acquisition and throughout the relationship.
- Establish minimum security requirements.
- Use document reviews, on-site assessments, process reviews, and independent audits.
- Verify third-party compliance with contracts, regulations, and security policies.

### SLR vs. SLA

- **Service-Level Requirement (SLR):** Customer's expected service/security requirements before agreement.
- **Service-Level Agreement (SLA):** Contractual agreement documenting service commitments and performance expectations.

### Authorization to Operate (ATO)
- Formal authorization permitting a system to operate under defined conditions.
- Insufficient documentation or control compliance may affect authorization.

## 10. Threat Modeling

### Purpose
- Identify, categorize, analyze, and prioritize threats to valuable assets.
- Preferably performed early in system design and maintained throughout the system life cycle.

### Threat Modeling Approaches

- **Asset-Centric:** Identify threats against valuable assets.
- **Attacker-Centric:** Analyze attacker motivations, capabilities, and techniques.
- **Software-Centric:** Examine software architecture and possible vulnerabilities.

### STRIDE — Threat Categorization

| Threat | Security Property Affected |
|---|---|
| Spoofing | Authentication |
| Tampering | Integrity |
| Repudiation | Nonrepudiation |
| Information Disclosure | Confidentiality |
| Denial of Service | Availability |
| Elevation of Privilege | Authorization |

### DREAD — Threat Prioritization

- **D — Damage Potential:** Severity of damage.
- **R — Reproducibility:** Ease of reproducing the attack.
- **E — Exploitability:** Ease of exploiting the vulnerability.
- **A — Affected Users:** Number/proportion of users affected.
- **D — Discoverability:** Ease of finding the vulnerability.

### PASTA — Seven Stages

**Process for Attack Simulation and Threat Analysis:** Risk-centric threat modeling methodology.

1. Define Objectives.
2. Define Technical Scope.
3. Application Decomposition and Analysis.
4. Threat Analysis.
5. Weakness and Vulnerability Analysis.
6. Attack Modeling and Simulation.
7. Risk Analysis and Management.

### VAST
- **Visual, Agile, and Simple Threat** modeling.
- Supports scalable threat modeling integrated with Agile development.

### Threat Modeling Process

1. Identify assets, architecture, and potential attackers.
2. Diagram system components and data flows.
3. Identify trust boundaries and entry points.
4. Decompose the application into smaller components.
5. Identify threats and vulnerabilities.
6. Rank threats based on likelihood and impact.
7. Select and implement appropriate countermeasures.

### Decomposition — Five Key Elements

- Trust Boundaries.
- Data Flow Paths.
- Input Points.
- Privileged Operations.
- Security Stance and Assumptions.

### Important Distinctions

- **Threat Modeling:** Identifies potential threats and attack paths, often proactively.
- **Threat Hunting:** Searches for evidence of malicious activity or compromise.
- **Vulnerability Assessment:** Identifies security weaknesses.
- **Penetration Testing:** Attempts authorized exploitation to evaluate security.
- **Risk Assessment:** Evaluates threats, vulnerabilities, likelihood, and business impact.

## 11. Supply Chain Risk Management (SCRM)

### Purpose
- Identify and reduce risks introduced by external suppliers, vendors, products, services, and software dependencies.
- Risks include tampering, counterfeit components, unauthorized firmware, malicious implants, and compromised third-party software.

### Security Controls

- Assess suppliers before onboarding.
- Establish minimum security and contractual requirements.
- Conduct periodic supplier assessments and monitoring.
- Verify software/hardware provenance and authenticity.
- Monitor vulnerabilities in supplied components.
- Evaluate supplier continuity and availability risks.

### Silicon Root of Trust (RoT)
- Hardware-based foundation for establishing system trust.
- Supports secure boot, integrity verification, and cryptographic operations.
- May support remote attestation.

### Physically Unclonable Function (PUF)
- Uses unique physical characteristics of hardware to derive device-specific responses.
- Supports device identification, authentication, and cryptographic key derivation.
- Useful in hardware authenticity and anti-counterfeiting controls.

### Software Bill of Materials (SBOM)
- Structured inventory of software components and dependencies.
- Identifies component names, versions, sources, and relationships.
- Supports vulnerability tracking, software transparency, and supply chain security.

### Key Distinctions

- **Silicon RoT:** Establishes a trusted hardware foundation.
- **PUF:** Provides hardware-derived uniqueness.
- **SBOM:** Provides software component/dependency transparency.
- **SCRM:** Manages risks across the supply chain, not only the direct supplier.
