## 1. Secure Design Foundations

### Subjects, Objects, and Access

- **Subject:** Active entity requesting access (user, application, process, computer, or organization).
- **Object:** Passive resource being accessed (file, service, database, printer, or even another process).
- **Access:** The requested operation, such as read, write, execute, delete, print, or modify.
- **Authorization / access control:** Determines which subject may perform which action on which object.
- **Roles change with the request:** If Process A requests data from Process B, B is the **object**. If B then requests data from Process C, B becomes the **subject**.
- <mark class="confident"> **Transitive trust:** A trusts B, and B trusts C; A may indirectly obtain access to C through B. This can bypass intended restrictions if the intermediate system grants access that the original requester should not have. </mark>
  - <mark class="confident"> **Example:** A user reaches a blocked website through an allowed VPN or proxy. </mark>

### Open vs. Closed Systems

| Concept | Easy Explanation | Example / Security Consideration |
|---|---|---|
| **Open system** | Uses widely agreed standards and APIs; designed for interoperability. | Windows, Linux, and macOS communicate through common networking standards; common interfaces can also be attack paths. |
| **Closed system** | Uses restricted/proprietary interfaces, often with limited integration. | Specialized proprietary device; attacks may require custom knowledge, but closed does **not** mean inherently secure. |
| **Open source** | Source code is available for inspection. | Code transparency, independent review. |
| **Closed source** | Source code is not generally publicly available. | Review and fixes depend more heavily on the vendor. |

- **Important:** *Open/closed system* describes **interoperability**; *open/closed source* describes **source-code availability**. These are different dimensions.
- **API (Application Programming Interface):** Defines permitted requests, response formats, and interaction rules between software/hardware components; may also define authentication and encryption requirements.

## 2. Core Secure Design Principles

### Secure Defaults / Restrictive Defaults

- Start a product with **secure, restrictive settings**, not maximum permissions or unnecessary features.
- Review vendor default configurations: factory defaults often favor ease of installation rather than security.
- **Example:** Disable unused services and change/remove default credentials before deploying a network device.
- **Memory:** *Default = deny/restrict unless access is needed.*

### Fail Securely — Failure Behavior

- **Fail-secure:** A failure does not accidentally bypass security restrictions.
- **Fail-soft:** Some system functions continue even after one component fails.
- **Physical-world fail-safe:** Priority is **human safety**; an emergency exit unlocks to allow escape.
- **Physical-world fail-secure:** Priority is **asset protection**; a vault remains locked on power failure.
- **Digital fail-open:** Traffic/operations continue when a security component fails; favors **availability** but may expose systems.
- **Digital fail-closed / fail-secure:** Access or traffic stops on failure; favors **confidentiality and integrity**, possibly sacrificing availability.

| Scenario | Behavior | Priority |
|---|---|---|
| Emergency exit door releases on power failure | Physical fail-safe / fail-open | People |
| Bank vault locks on failure | Physical fail-secure / fail-closed | Assets |
| Firewall outage allows traffic through | Digital fail-open | Availability |
| Firewall outage blocks traffic | Digital fail-closed / fail-secure | Confidentiality and integrity |
| One application crashes but the operating system continues | Fail-soft | Continued partial operation |

- **Exam caution:** The source chapter uses *fail-safe* differently depending on physical vs. digital context. **Always read the scenario and the priority.**
- **Exception handling:** Anticipate and handle errors (e.g., `try/catch`) to prevent unsafe behavior.
- **Input validation/sanitization:** Check length, format, and disallowed input; handle special characters carefully to reduce misuse.
- **Exam clue:** A device must choose how to behave after failure → identify whether the scenario prioritizes **human safety, asset security, or availability**.

### Keep It Simple and Small (KISS)

- Fewer components, features, and lines of code generally mean less complexity, fewer potential defects, and a smaller attack surface.
- **DRY (Don't Repeat Yourself):** Avoid duplicated code, which is harder to maintain consistently.
- **Computing minimalism:** Use only necessary hardware/software resources.
- **Rule of Least Power:** Choose the least powerful programming language adequate for the task.
- <mark class="confident">  **Worse Is Better:** A simpler implementation with fewer capabilities may be preferable to an overcomplicated one. </mark>
- <mark class="confident"> **YAGNI (You Aren't Gonna Need It):** Do not implement speculative features before they are necessary. </mark>
- **Example:** A small, tightly scoped API is easier to test and secure than a service exposing unused endpoints.

### Zero Trust vs. Trust but Verify

- **Traditional trust but verify:** Internal users/devices are initially treated as trusted; periodic checks may follow. This leaves exposure to insider threats and lateral movement.
- **Zero trust:** **Never trust, always verify**; assume a breach is possible, whether the request originates internally or externally.
- Authenticate and authorize each access request; protect sessions, use **least privilege**, and continuously assess identity, device, and behavior.
- <mark class="confident">  **Microsegmentation:** Divide a network into small security zones with controlled, monitored communications between them; limits lateral movement. </mark>
- <mark class="confident">  **Typical enabling controls:** IAM, MFA, internal segmentation firewalls, device/endpoint security, monitoring, logging. </mark>
- <mark class="confident">  **Air gap:** Physical isolation from other networks, including wired and wireless links; a Faraday cage may help block wireless connectivity. 
(A Faraday cage is an enclosure made of electrically conductive material (such as copper, aluminium, or metal mesh) that shields the objects inside from external electromagnetic fields and reduces electromagnetic signals escaping from inside.) </mark>
- **Example:** Even an employee inside the corporate network must authenticate and be authorized before accessing a sensitive production workload.
- <mark class="confident"> **Reference:** NIST SP 800-207, Zero Trust Architecture. (It explains how organizations should design security when users, devices, and applications cannot be automatically trusted just because they are inside the corporate network.) </mark>


<mark class="confident"> ## Privacy by Design (PbD) — 7 Foundational Principles </mark>
1. **Proactive, Not Reactive:** Identify and prevent privacy risks before they occur rather than fixing problems after a breach. Example: Conduct a Privacy Impact Assessment (PIA) before launching an application.

2. **Privacy as the Default:** Personal information should be protected automatically without requiring users to change settings. Example: User profiles are private by default rather than publicly visible.

3. **Privacy Embedded into Design:** Integrate privacy protection into system architecture and the Software Development Life Cycle (SDLC), rather than adding it afterward. Example: Design applications to collect minimal personal data and encrypt sensitive information.

4. **Full Functionality (Positive-Sum):** Achieve both privacy protection and business functionality without unnecessarily sacrificing either. Example: Analyze customer trends using anonymized data instead of revealing individual identities.

5. **End-to-End Lifecycle Protection:** Protect personal data throughout its lifecycle, from collection and storage to use, sharing, and secure disposal. Example: Encrypt customer records and securely delete them after the retention period.

6. **Visibility and Transparency:** Clearly explain how personal data is collected, processed, shared, and protected so practices can be independently verified. Example: Publish understandable privacy notices and maintain auditable privacy controls.

7. **Respect for User Privacy:** Prioritize individuals' privacy rights by providing meaningful choices, informed consent, and control over personal information. Example: Allow users to review their data, change privacy preferences, and request deletion.


<mark class="confident">  ### Secure Access Service Edge (SASE) </mark>

- **SASE:** Cloud-delivered architecture combining **WAN/network connectivity** and **network security services** for distributed users, devices, and cloud applications.
- Uses identity/device-centered access, often incorporating **Zero Trust Network Access (ZTNA)**.
- **Important characteristics:** Cloud-native service delivery, distributed edge, consistent policy enforcement, scalable access, continuous monitoring.
- **Example:** A remote employee accesses corporate SaaS through identity-based, security-inspected connectivity rather than automatically trusting a corporate network perimeter.
- **Memory:** **SASE = Networking + Security delivered near users / through the cloud.**
- **Exam clue:** Secure access for geographically distributed workers using cloud-delivered networking and security → **SASE**; deciding whether a request deserves trust → **Zero Trust**.

## 3. Techniques for Confidentiality, Integrity, and Availability

| Technique | Meaning | Example |
|---|---|---|
| **Confinement** | Restrict a process to approved actions and resources. | Sandbox a suspicious application. |
| **Bounds** | Define permitted addresses, resources, and authority levels. | A process cannot read another process's memory. |
| **Isolation** | Separate processes so one cannot interfere with another. | One application crash does not corrupt another. |
| **Access control** | Permit subject-to-object actions only when authorized. | User may read a file but not modify it. |

- **Memory:** **Confinement = restriction; Bounds = limits; Isolation = separation.**
- **Exam clue:** One app must not access another app's memory → **process isolation and bounds**; restricting what a process can do → **confinement**.
- **Trust:** Security mechanisms/capabilities are present.
- **Assurance:** Degree of confidence that the security mechanisms **actually work reliably**.
- Assurance requires **ongoing reassessment**, especially after major changes, patches, or security incidents.

## 4. Security Models — Foundations

- **Security model:** Formal representation of security rules so designers can implement and evaluate security policy.
- **Security token:** Separate item carrying security attributes for a resource.
- **Capability list:** Subject-centered record of what objects/actions a subject is permitted to access.
- **Security label:** Attribute attached to an object, often enduring and hard to change, indicating its security classification.

<mark class="confident">  ### Trusted Computing Base (TCB), Security Kernel, Reference Monitor </mark>

| Term | Definition / Memory Aid |
|---|---|
| **Trusted Computing Base (TCB)** | **Hardware + software + controls** responsible for enforcing security policy. Should be **as small as possible** so it can be evaluated. |
| **Security perimeter** | Logical boundary between TCB and the rest of the system. |
| **Trusted path** | Protected communication channel into/with the TCB. |
| **Reference monitor** | **Concept** of checking *every* subject-to-object access request against the security policy. |
| **Security kernel** | **Implementation** (hardware/software) of the reference-monitor function. |

- **Example:** Before a process opens a protected file, the security kernel enforces the reference monitor's access decision.
- **Memory:** **Reference monitor = idea; Security kernel = working implementation.**
- **Exam clue:** The hardware/software portion that enforces security policy → **TCB**; the conceptual check for every access → **reference monitor**.

### State Machine Model

- System must begin in a **secure state** and transition **only into other secure states**.
- A **state** is a snapshot of the system; a **transition** is a change following input or activity.
- **Example:** If every allowed login, file-open, and permission-change operation preserves the security policy, the system remains secure.

### Information Flow Model

- Controls **where and how information can flow** between subjects/objects and security levels.
- Prevents unauthorized information transfers and considers hidden/covert flow paths.
- **Example:** Stop sensitive data from moving into an unauthorized low-security environment.

### Noninterference Model

- Activity at a **higher security level** should not observably affect a **lower-level subject**, so low-level users cannot infer confidential information.
- **Example:** A low-security application must not deduce a classified process's activity from visible changes in system behavior.

### Composition Theories

| Theory | Meaning | Memory |
|---|---|---|
| **Cascading** | Output from System A becomes input to System B. | A → B |
| **Feedback** | A feeds B, and B subsequently feeds A. | A ↔ B |
| **Hookup** | A feeds B **and** an external entity. | A → B + outside |

### Take–Grant Model

- Graph-based model showing how access rights are acquired, transferred, created, or removed.
- **Take:** Obtain rights from another subject/relationship.
- **Grant:** Pass rights to another subject/object.
- **Create:** Create new rights.
- **Remove:** Remove rights.
- **Example:** Permission inheritance/copying may spread rights beyond the original subject.

### Access Control Matrix

- Table with **subjects as rows**, **objects as columns**, and **rights in each cell**.
- <mark class="confident"> **Access Control List (ACL): Object-centric** — who can access **this file**, and how? </mark>
- <mark class="confident"> **Capability List: Subject-centric** — which files/resources can **this user** access, and how? </mark>

| | File A | Printer |
|---|---|---|
| **Alice** | Read | Print |
| **Bob** | Read, Write | No access |

- **Memory:** **ACL = object's list; Capability = subject's list.**
- **Exam clue:** “Who can access this particular file?” → **ACL**; “What can this particular user access?” → **capability list**.

## 5. Major Security Models

### Bell–LaPadula (BLP) — Confidentiality

- **Goal:** Prevent disclosure of information from higher to lower security classifications.
- Uses **mandatory access controls (MAC)** and multilevel/lattice-based security.
- **Simple Security Property (`ss`) = NO READ UP.** A lower-cleared subject may not read higher-classified data.
- **Star Property (`*`) = NO WRITE DOWN.** A subject may not write classified information to a lower level.
- **Discretionary Security Property:** Access matrix further restricts access (e.g., need to know).
- **Example:** An employee cleared for Secret cannot read Top Secret and cannot copy Secret material into an Unclassified file.
- **Special case:** A designated **trusted subject** may be allowed to write down for authorized declassification.
- **Limitations in the source:** Primarily confidentiality; does not fully address covert channels or modern file sharing/networking.
- **Memory:** **BLP = Keep secrets from leaking DOWN.**
- **Exam clue:** Classified government information / preventing disclosure across security levels → **Bell–LaPadula**.

### Biba — Integrity

- **Goal:** Prevent lower-integrity information from contaminating higher-integrity information.
- **Simple Integrity Property = NO READ DOWN.** A high-integrity subject must not read untrusted, lower-integrity data.
- **Star Integrity Property (`*`) = NO WRITE UP.** A lower-integrity subject must not modify higher-integrity objects.
- **Invocation Property:** Lower-integrity processes may not invoke higher-integrity processes.
- **Example:** An untrusted public feed must not directly alter or contaminate validated financial records.
- **Limitations in the source:** Protects integrity, not confidentiality/availability; does not solve covert channels or classification administration.
- **Memory:** **Biba = Keep bad/untrusted data from rising UP.**
- **Exam clue:** Prevent untrusted data from contaminating highly trusted records → **Biba**.

| Model | Primary Goal | Simple (`ss`): Reading | Star (`*`): Writing |
|---|---|---|---|
| **Bell–LaPadula** | **Confidentiality** | **NO READ UP** | **NO WRITE DOWN** |
| **Biba** | **Integrity** | **NO READ DOWN** | **NO WRITE UP** |

> <mark class="confident">  **Remember:** In both models, **Simple = Read**, **Star = Write**. Biba reverses Bell–LaPadula's directions. </mark>

### Clark–Wilson — Commercial Data Integrity

- <mark class="confident">  **Goal:** Maintain **integrity through well-formed transactions and separation of duties**. </mark>
- **Subject → approved program/transaction → object** (the **access-control triplet**).
- Users cannot directly change protected data; changes must pass through approved programs.</mark>
- <mark class="confident"> **CDI (Constrained Data Item):** Protected data whose integrity must be maintained. </mark>
- <mark class="confident"> **UDI (Unconstrained Data Item):** Unvalidated/input data not yet under integrity constraints. </mark>
- <mark class="confident"> **IVP (Integrity Verification Procedure):** Checks data integrity.
- <mark class="confident"> **TP (Transformation Procedure):** Authorized operation that can modify a CDI. </mark>
- **Example:** A bank balance may be updated only through an approved deposit/withdrawal transaction, not by directly editing the database row.
- **Memory:** **Clark–Wilson = Controlled transactions + Separation of Duties.**
- **Exam clue:** Business records are changed only through approved intermediary programs; **CDI/UDI/IVP/TP** terminology → **Clark–Wilson**.

### Brewer and Nash — Conflict of Interest

- Also historically called the **Chinese Wall** model; source recommends **Brewer and Nash / ethical wall** terminology.
- <mark class="confident">  **Dynamic access controls based on previous access/activity** prevent conflicts of interest.</mark>
- After accessing one company's confidential data, a subject is restricted from accessing a competing company's data in the same conflict class.
- **Example:** A consultant who reviews confidential Company A plans cannot access competing Company B's confidential plans.
- **Memory:** **Brewer and Nash = Past access changes future access.**
- **Exam clue:** Consultant must not access confidential information belonging to competing clients → **Brewer and Nash**.

### Security Models at a Glance

| Model | Exam Keywords |
|---|---|
| **State machine** | Every state and transition remains secure |
| **Information flow** | Control permitted movement of information |
| **Noninterference** | High-level activity must not reveal information to lower level |
| **Take–Grant** | Rights transferred through take/grant/create/remove |
| **Access control matrix** | Subjects × objects × permissions |
| **Bell–LaPadula** | Confidentiality; no read up/no write down |
| **Biba** | Integrity; no read down/no write up |
| **Clark–Wilson** | Integrity; well-formed transactions; separation of duties |
| **Brewer and Nash** | Dynamic access; conflicts of interest |

### What Does “Star” Mean?

- **Star (`*`) property** is the **write rule** in Bell–LaPadula and Biba; there is **no separate formal security model called “Star Model”** in this chapter.
- **CSA STAR:** Cloud Security Alliance **Security Trust Assurance and Risk** program, related to cloud-provider assurance; unrelated to the model's star property.

<mark class="confident"> ## 6. Security Product Evaluation — Common Criteria </mark>

- **Common Criteria (CC):** International framework for evaluating specified IT-product security claims and assurance; associated with **ISO/IEC 15408**.
- Replaced earlier evaluation systems **TCSEC** (US) and **ITSEC** (Europe).
- Certification/ratings improve confidence **but do not guarantee** that a product is vulnerability-free or secure in every real deployment.

| Term | Meaning | Easy Memory |
|---|---|---|
| **TOE (Target of Evaluation)** | Product/system configuration being evaluated. | **What** is tested |
| **PP (Protection Profile)** | Desired security requirements for a type of product, typically the purchaser's needs. | Buyer: **“I WANT”** |
| **ST (Security Target)** | Vendor's claims about the TOE's security functions and assurance. | Vendor: **“I PROVIDE”** |
| **EAL (Evaluation Assurance Level)** | Degree of **evaluation assurance**, not a guarantee of invulnerability. | **How rigorously** evaluated |

### EAL1–EAL7 (Increasing Evaluation Rigor)

| EAL | Short Memory Cue |
|---|---|
| **EAL1** | Functionally tested |
| **EAL2** | Structurally tested |
| **EAL3** | Methodically tested and checked |
| **EAL4** | Methodically designed, tested, and reviewed |
| **EAL5** | Semi-formal design/testing and higher assurance |
| **EAL6** | Semi-formal verification and testing for high-risk use |
| **EAL7** | Formal verification/design/testing; highest evaluation rigor |

- **Limitations identified in the guide:** CC evaluates a stated **TOE**, not all user behavior, administration, physical controls, or every aspect of deployment.
- **Exam clue:** Buyer needs documented product security requirements → **PP**; vendor describes offered security claims → **ST**.
- **Important:** EAL ratings describe evaluation assurance of the specified TOE; they **do not** mean an EAL7 product is invulnerable or necessarily more suitable for every business scenario.
- **Package:** Group of additional security requirements/features that can be included in the evaluation target.

## 7. Authorization to Operate (ATO)

- <mark class="confident"> **ATO:** Formal decision permitting operation of a specified system/environment **with acknowledged residual risk**. </mark>
- **AO (Authorizing Official):** Official with authority to review risk and grant or deny authorization.
- **ATO is not a product certificate:** It is a **risk-acceptance decision for a system's operation**.
- The guide states ATOs have **often** used a 3-year period, but validity varies and may be reconsidered after significant security changes or breaches.
- **Four authorization decisions described in the chapter:**
  1. **Authorization to Operate:** Operate when risk is acceptable.
  2. **Common Control Authorization:** Authorize shared/common security controls.
  3. **Authorization to Use:** Accept an external provider's or another AO's previously authorized service/system as appropriate.
  4. **Denial of Authorization:** Risk is unacceptable; operation is not approved.
- **Memory:** **CC = evaluated product; ATO = approved system operation and accepted risk.**
- **Exam clue:** Official acceptance of *residual risk* before a system is used → **ATO**; selecting a product according to evaluated security assurance → **Common Criteria**.

## 8. Security Capabilities of Information Systems

| Capability | Purpose | Example |
|---|---|---|
| **Memory protection** | Prevent one process accessing memory not assigned to it. | OS stops unauthorized cross-process memory access. |
| **Virtualization** | Host isolated operating environments; also useful for controlled testing. | VM used to test suspicious software. |
| <mark class="confident"> **TPM (Trusted Platform Module)** | <mark class="confident"> Hardware cryptoprocessor used for cryptographic operations/key protection, commonly supporting storage encryption. | <mark class="confident"> Device holds or protects disk-encryption key material. </mark> |
| <mark class="confident"> **HSM (Hardware Security Module)** | <mark class="confident"> Hardware-based key management/cryptographic operations with tamper protection; may be a chip, card, peripheral, or network device.  | <mark class="confident"> Dedicated appliance protects signing keys. </mark> |
| **Constrained/restricted interface** | Show or permit only functions allowed for a user's privileges. | Admin menu hidden/disabled for ordinary users. |
| **Fault tolerance** | Keep working despite component failures using redundancy. | RAID or server failover cluster. |
| **Encryption / decryption** | Convert plaintext ↔ ciphertext to protect information. | Encrypt data before storage/transmission. |

- **TPM vs HSM:** TPM is a particular device-oriented hardware cryptoprocessor; HSM is a broader hardware-security category.
- **Restricted interfaces** are a practical example of the **Clark–Wilson** controlled-program approach.
- **Fault tolerance** supports **availability** and reduces single points of failure.

## 9. Information System Life Cycle

| Stage | Simple Explanation | Example |
|---|---|---|
| **1. Stakeholder needs and requirements** | Find out what users, managers, and regulators require. | Identify required user workflows and compliance needs. |
| **2. Requirements analysis** | Analyze functional/nonfunctional requirements and constraints. | Define access-control and uptime requirements. |
| **3. Architectural design** | Design components, interfaces, and data flows. | Draw system architecture and trust boundaries. |
| **4. Development / implementation** | Build and configure the system. | Develop services and implement controls. |
| **5. Integration** | Combine components into a working system. | Connect authentication and application services. |
| **6. Verification and validation** | Confirm correct construction and intended usefulness. | Test specifications and business acceptance. |
| **7. Transition / deployment** | Move into production/operational use. | Release services to production users. |
| **8. Operations and maintenance / sustainment** | Operate, monitor, support, patch, and improve. | Apply security updates and monitor logs. |
| **9. Retirement / disposal** | Decommission securely and handle data/disposal obligations. | Sanitize retired drives and decommission access. |

- <mark class="confident"/> **Verification:** **Are we building the system right?** (Meets specifications.)
- <mark class="confident"/> **Validation:** **Are we building the right system?** (Meets stakeholder needs/intended purpose.)
- **Security must be designed in throughout the lifecycle**, not added only at deployment.
- <mark class="confident"/>**Exam clue:** “Does it satisfy the specification?” → **Verification**; “Does it solve the stakeholder's actual need?” → **Validation**.

### Last-Minute Memory Prompts

- **Simple property = READ; Star (`*`) property = WRITE.** This applies to both Bell–LaPadula and Biba.
- **BLP:** No Read Up, No Write Down → prevent secret-data disclosure.
- **Biba:** No Read Down, No Write Up → prevent integrity contamination.
- **Clark–Wilson:** Subject → approved TP → CDI; IVP checks integrity; UDI is unvalidated input.
- **Brewer and Nash:** Previous client-data access limits future access to competitors.
- **Reference Monitor = Concept; Security Kernel = Implementation; TCB = Trusted foundation.**
- **Physical emergency exits:** Protect people; **digital fail-closed firewall:** protect confidentiality/integrity.
- **Zero Trust:** Never trust by location; verify and monitor access continually.
- **PP = “I want”; ST = “I provide”; TOE = “What is evaluated”; EAL = “Evaluation assurance.”**
- **ATO:** Authorizing Official decides whether remaining risk is acceptable.
