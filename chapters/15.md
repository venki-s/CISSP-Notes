
# Chapter 15 — Security Assessment and Testing

**CISSP Domains: 6 and 8**

---

## 1. Security Testing vs. Assessment vs. Audit

| Activity | Purpose |
|---|---|
| Security Testing | Verify that security controls function correctly |
| Security Assessment | Evaluate security posture, risks, and weaknesses; recommend improvements |
| Security Audit | Independently evaluate controls against defined requirements |

- **Testing:** Focuses on control functionality.
- **Assessment:** Considers threats, vulnerabilities, risks, and business context.
- **Audit:** Requires auditor independence and objective evidence.
- Testing frequency should be **risk-based**, considering asset criticality, sensitivity, changes, threats, and business impact.
- Testing strategies must cover on-premises, cloud, and hybrid environments.

### NIST SP 800-53A Assessment Objects
- **Specifications:** Policies, procedures, requirements, and designs.
- **Mechanisms:** Hardware, software, and firmware controls.
- **Activities:** Actions performed to operate controls.
- **Individuals:** People responsible for implementing and operating controls.

Assessment methods include examination, interviews, and testing.

---

## 2. Security Audits

| Type | Distinguishing Characteristic |
|---|---|
| Internal | Conducted by independent internal audit staff |
| External | Independent outside auditors hired by the organization |
| Third-Party | Initiated/controlled by another organization, such as a customer or regulator |

**Exam:** Audit independence is essential. External and third-party audits differ in who initiates and controls them.

### SOC Reports

| Report | Purpose |
|---|---|
| SOC 1 | Controls relevant to financial reporting |
| SOC 2 | Security and other trust-service controls; restricted-use report |
| SOC 3 | General-use/public trust-service assurance report |

### SOC Type I vs. Type II
- **Type I:** Design suitability of controls at a point in time.
- **Type II:** Design and **operating effectiveness** over a period of time.
- Type II provides greater assurance of control effectiveness.

### Audit Standards
- **COBIT:** IT governance and control framework.
- **ISO 27001:** ISMS requirements; supports certification.
- **ISO 27002:** Information security control guidance.
- **SSAE 18 / ISAE 3402:** Attestation and service-organization assurance standards.

## 3. Vulnerability Assessment

- Identifies security weaknesses that could be exploited.
- Usually uses automated scanning.
- Does not normally attempt actual exploitation.
- Results should be prioritized according to business risk.

### Vulnerability Management
1. **Detection:** Identify potential vulnerabilities.
2. **Validation:** Confirm findings and eliminate false positives.
3. **Remediation:** Patch, reconfigure, or implement compensating controls.
4. **Verification:** Retest to confirm remediation.

### SCAP Components

| Component | Purpose |
|---|---|
| CVE | Unique vulnerability identifiers |
| CVSS | Vulnerability severity scoring |
| CCE | Configuration issue identifiers |
| CPE | Platform/product identifiers |
| XCCDF | Security checklist definitions |
| OVAL | Machine-readable security test definitions |

**Important:** CVSS measures vulnerability severity, not complete organizational risk.

---

## 4. Vulnerability Scanning

| Scan Type | Purpose |
|---|---|
| Network Discovery | Identify hosts and exposed ports |
| Network Vulnerability | Identify known system/service vulnerabilities |
| Web Application | Detect application-level vulnerabilities |
| Database | Identify database-related weaknesses |

### Authenticated vs. Unauthenticated
- **Authenticated:** Uses authorized credentials to inspect configurations and patch states; generally more complete.
- **Unauthenticated:** Tests without privileged access; more closely resembles an external attacker's perspective.

### False Positive vs. False Negative
- **False Positive:** Reports a vulnerability that does not exist.
- **False Negative:** Misses an existing vulnerability; potentially more dangerous.

### Limitations
- Traditional signature-based scanners may miss zero-day vulnerabilities.
- Scanner findings require validation.
- Network scans may miss application logic flaws.

### Common Tools
- **Nmap:** Network discovery and port scanning.
- **OpenVAS:** Vulnerability scanning.
- **sqlmap:** SQL injection assessment.
- **Aircrack-ng:** Wireless security assessment.

---

## 5. Network Scanning Techniques

| Technique | Characteristic |
|---|---|
| SYN Scan | Half-open TCP scan |
| TCP Connect | Completes TCP handshake |
| ACK Scan | Helps assess firewall filtering |
| UDP Scan | Probes UDP services |
| Xmas Scan | FIN + PSH + URG flags |

### Port States
- **Open:** Service accepts connections.
- **Closed:** Reachable but no service listening.
- **Filtered:** Firewall/filter prevents determination.
- **Unfiltered:** Reachable, but open/closed status unknown.
- **Open/Filtered:** Cannot distinguish between these states.

### Related Terms
- **Banner Grabbing:** Identifies service and version information.
- **netstat:** Displays local network connections and listening ports.

**Exam:** Scanning must be authorized by the system/network owner.

## 6. Vulnerability Scanning vs. Penetration Testing

| Vulnerability Scanning | Penetration Testing |
|---|---|
| Identifies potential weaknesses | Attempts to exploit weaknesses |
| Primarily automated | Requires skilled testers |
| Usually broad and repeatable | Usually focused and scenario-driven |
| May produce false positives | Demonstrates exploitability |
| Generally less intrusive | Greater operational risk |

### NIST SP 800-115 Penetration Testing Phases
1. **Planning:** Authorization, scope, rules of engagement.
2. **Discovery:** Reconnaissance, scanning, vulnerability analysis.
3. **Attack:** Exploit identified weaknesses.
4. **Reporting:** Findings, risks, and recommendations.

### Knowledge Levels
- **White Box:** Full/detailed knowledge of the target.
- **Gray Box:** Partial knowledge.
- **Black Box:** No prior internal knowledge.

### Critical Requirements
- Obtain explicit authorization before testing.
- Define scope, exclusions, and rules of engagement.
- Consider operational disruption and data integrity risks.

**Exam:** Planning and authorization come before active testing.

---

## 7. Breach and Attack Simulation (BAS)

- Automates simulation of malicious activity to test defensive controls.
- Evaluates whether security controls detect or block simulated threats.
- Identifies detection and prevention gaps.
- Unlike full penetration testing, BAS generally does not require actual system compromise.

**Distinction:** Penetration testing demonstrates exploitation; BAS validates defensive-control responses.

---

## 8. Compliance Testing

- Maps regulatory obligations to corresponding security controls.
- Periodically verifies that required controls are operating effectively.
- Identifies gaps requiring remediation.

**Exam:** Compliance checks evaluate whether regulatory and policy requirements are being satisfied.

---

## 9. Code Review

- Examines code for security, reliability, and functional defects.
- Peer review uses developers other than the original author.
- May include manual inspections or automated analysis.

### Fagan Inspection — Six Stages
1. Planning
2. Overview
3. Preparation
4. Inspection
5. Rework
6. Follow-up

**Exam:** Formal code inspection with defined stages and entry/exit criteria = Fagan Inspection.

## 10. Application Security Testing

| Technique | Key Characteristic |
|---|---|
| SAST | Analyzes code without executing it |
| DAST | Tests the running application |
| IAST | Uses runtime instrumentation/analysis |
| RASP | Protects the application during execution |

### SAST
- Static application security testing.
- Examines source or compiled code without execution.
- Supports early detection during development.

### DAST
- Dynamic application security testing.
- Evaluates running applications.
- Can detect SQL injection, XSS, and similar flaws.
- Useful when source code is unavailable.

### IAST
- Interactive application security testing.
- Observes application behavior during execution.
- Combines runtime testing with application-level insight.

### RASP
- Runtime application self-protection.
- Monitors/intercepts application operations.
- Can prevent or block malicious activity.

**Exam:** RASP is primarily a protection mechanism; SAST, DAST, and IAST are testing techniques.

---

## 11. Fuzz Testing

- Dynamic testing that supplies invalid, unexpected, or random inputs.
- Detects crashes, buffer overflows, and unexpected behavior.

### Types
- **Mutation Fuzzing:** Alters existing inputs; also called dumb fuzzing.
- **Generational Fuzzing:** Generates inputs using a data model; also called intelligent fuzzing.

### Limitation
- Does not guarantee complete test coverage.
- May miss complex business logic vulnerabilities.

---

## 12. Software Testing Techniques

### Interface Testing
Validates security and correct interactions through:
- **APIs:** Authentication, authorization, input handling.
- **User Interfaces:** Secure and correct user interaction.
- **Network Interfaces:** Secure data transmission and error handling.
- **Physical Interfaces:** Safe interaction with physical systems.

### Misuse Case Testing
- Also called abuse case testing.
- Tests known ways an application could be intentionally misused.
- Example: Attempting unauthorized access to another customer's account.

### Synthetic Transactions
- Scripted transactions with predefined expected outcomes.
- Compare actual and expected results.

### Benchmarks
- Compare system performance/effectiveness against defined baselines.

---

## 13. Test Coverage Analysis

Measures how much of the application has been exercised by testing.

| Coverage | Measures |
|---|---|
| Statement | Whether statements execute |
| Branch | Whether each decision outcome executes |
| Condition | Whether individual logical conditions are exercised |
| Function | Whether functions are executed |
| Loop | Whether loops execute zero, once, and multiple times |

**Important:** High test coverage does not guarantee defect-free or secure software.

---

## 14. Website Monitoring

### Passive Monitoring
- Observes real user traffic and activity.
- **Real User Monitoring (RUM)** is a form of passive monitoring.
- Useful for identifying problems experienced by actual users.

### Active/Synthetic Monitoring
- Generates artificial transactions.
- Tests website availability and performance.
- May detect issues before users encounter them.

**Exam:** Real user activity = Passive; simulated transactions = Synthetic.

## 15. Security Exercises

| Team | Responsibility |
|---|---|
| Red | Offensive testing / attack simulation |
| Blue | Defense, detection, and response |
| White | Exercise supervision, rules, and observation |
| Purple | Red and blue collaboration to improve defenses |

### Other Exercises
- **Capture the Flag (CTF):** Complete predefined security objectives.
- **Tabletop Exercise:** Discussion-based simulation of a security incident.

## 16. Log Reviews and Account Reviews

### Log Reviews
- Detect misuse, suspicious activity, and control failures.
- **SIEM:** Collects and correlates security events.
- **NTP:** Synchronizes timestamps for accurate event reconstruction.
- **NetFlow:** Provides connection and traffic-volume information.
- Privileged activity requires particular monitoring.

### Account Management Reviews
- Compare actual permissions with approved permissions.
- Identify excessive privileges, unauthorized modifications, and terminated accounts.
- Can use complete reviews or random sampling.
- Sampling must be unbiased and representative.

**Exam:** Detect privilege creep or unauthorized account access through periodic account reviews.

---

## 17. Backup, BC/DR, and Training Verification

### Backup Verification
- Review backup logs and integrity checks.
- Perform restoration tests to verify recoverability.
- Backup success alone does not prove successful restoration.

### BC/DR
- Periodically test continuity and recovery controls.
- Verify readiness to respond to disruptions.

### Training and Awareness
- Provide role-specific initial training and recurring awareness.
- Use phishing simulations to measure awareness effectiveness.

---

## 18. KPI vs. KRI

### Key Performance Indicator (KPI)
Measures effectiveness or efficiency of a security process.

Examples:
- Average vulnerability remediation time.
- Percentage of completed access reviews.
- Percentage of required security training completed.

### Key Risk Indicator (KRI)
Indicates changing security exposure.

Examples:
- Number of critical unremediated vulnerabilities.
- Increasing compromised-account incidents.
- Repeat serious audit findings.

**Exam:** KPI = Performance; KRI = Risk exposure.

---

## 19. Reporting, Remediation, and Ethical Disclosure

### Reporting
- Communicate findings, severity, business impact, and recommendations.
- Present actionable information to management.

### Remediation
- Prioritize findings based on risk.
- Implement corrective actions or compensating controls.
- Retest to validate effectiveness.

### Exception Handling
- Document deviations from security requirements.
- Obtain appropriate risk-owner approval.
- Review exceptions periodically.

### Ethical Disclosure
- Privately notify vendors of newly discovered vulnerabilities.
- Allow reasonable time for remediation.
- Use coordinated disclosure to reduce harm.

# Key CISSP Distinctions — Final Revision

1. Testing = Verify controls; Assessment = Evaluate security posture; Audit = Independent evaluation.
2. SOC 1 = Financial; SOC 2 = Restricted-use trust assurance; SOC 3 = Public/general-use assurance.
3. Type I = Design at a point in time; Type II = Operating effectiveness over time.
4. CVE = Identifier; CVSS = Severity score.
5. Discovery Scan = Open ports; Vulnerability Scan = Known weaknesses; Pen Test = Exploitation.
6. False Positive = False alarm; False Negative = Missed vulnerability.
7. Authenticated Scan = More complete internal configuration inspection.
8. Pen Test = Planning → Discovery → Attack → Reporting.
9. White Box = Full knowledge; Gray Box = Partial; Black Box = None.
10. SAST = No execution; DAST = Runtime; IAST = Instrumented runtime; RASP = Runtime protection.
11. Mutation Fuzzing = Modify inputs; Generational Fuzzing = Create inputs from a model.
12. Misuse Case = Test deliberate application abuse.
13. Passive Monitoring = Real users; Synthetic Monitoring = Artificial transactions.
14. Red = Attack; Blue = Defend; White = Supervise; Purple = Collaborate.
15. Account Review = Actual vs. approved permissions.
16. Backup Verification = Confirm restoration works.
17. KPI = Process performance; KRI = Risk exposure.
18. Audit findings require risk-based remediation and verification.
