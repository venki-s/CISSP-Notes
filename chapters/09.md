# CISSP Chapter 9 — Security Vulnerabilities, Threats, and Countermeasures

**Domain 3: Security Architecture and Engineering**  
**Revision focus:** Understand architectural weaknesses, the resulting risk, and the most appropriate security control. Technical background that does not add much to CISSP decision-making is deliberately condensed.

## 1. Shared Responsibility and Data Jurisdiction

- **Shared responsibility:** Security is not solely the CISO/security team's job. Management, employees, auditors, suppliers, and cloud providers have defined security responsibilities. For third-party/cloud services, responsibilities must be explicitly allocated rather than assumed.
- **Responsible disclosure:** Report discovered vulnerabilities to the appropriate vendor or authorized information-sharing body.
- **IoC (Indicator of Compromise):** Observable evidence suggesting malicious activity, such as a suspicious file hash or network indicator.
- **STIX (Structured Threat Information eXpression):** Standardized **format/language** for describing cyberthreat intelligence.
- **TAXII (Trusted Automated eXchange of Intelligence Information):** **Protocol/services** for exchanging threat intelligence, including STIX data.
- **AIS (Automated Indicator Sharing):** Initiative for automated sharing of threat indicators between government and private-sector participants.

| Concept | Meaning | CISSP clue |
|---|---|---|
| **Data localization** | Data must be stored/processed inside specified geographical borders. | **Where** must the data reside? |
| **Data sovereignty** | Data is subject to applicable national/regional legal jurisdiction and authority. | **Whose laws** govern the data? |
| **Data portability** | Individuals can securely transfer their personal data between services. | Moving personal data between providers. |

## 2. CPU, Privileges, and Process Protection

- **Multitasking:** OS manages multiple tasks/processes; on one core, execution is time-sliced.
- **Multicore:** One physical CPU contains multiple processing cores.
- **Multiprocessing:** Uses multiple processors/cores for execution.
- **Multiprogramming:** Switches to other programs when one waits (e.g., for I/O) to improve utilization.
- **Multithreading:** Multiple threads execute within **one process**, usually sharing its address space.
- **Processor affinity:** Assigning or preferring a process/thread to run on particular CPU(s)/core(s).

### Protection rings and modes

| Ring / mode | Main meaning |
|---|---|
| **Ring 0 / kernel mode / supervisor mode** | Highest privilege; OS kernel and sensitive system operations. |
| **Ring 3 / user mode / problem mode** | Lower privilege; ordinary applications must request privileged services via system calls. |
| **Rings 1–2** | Intermediate privilege levels in the conceptual four-ring design; many modern OSs primarily use Rings 0 and 3. |

- **Security purpose:** Isolate less-trusted applications from the OS kernel; enforce privilege boundaries and **mediated access**.
- **Process isolation:** One process cannot freely read/write another's memory; helps prevent disclosure and corruption.
- **Hardware segmentation:** Physical hardware-based separation rather than logical process-only separation; stronger but costlier/less common.
- **Process states:** **Ready → Running → Waiting** (e.g., for I/O) → Ready; **Stopped/terminated** when complete. *Supervisor* describes privileged execution, not the usual lifecycle queue state.
- **Exam clue:** Unauthorized application attempts to alter kernel memory → **privilege separation, process isolation, memory protection**.

## 3. Memory and Storage — Only Security-Relevant Points

| Technology / term | Remember |
|---|---|
| **ROM / PROM** | Nonvolatile; ROM fixed, PROM programmable once. |
| **EPROM** | Erasable and reprogrammable; traditional UV EPROM erased using ultraviolet light. |
| **EEPROM / flash** | Electrically erasable nonvolatile memory; flash typically erased in blocks. |
| **RAM** | Volatile working memory; may briefly retain recoverable information after power loss. |
| **DRAM / SRAM** | DRAM needs refresh and commonly serves as main memory; SRAM is faster, costlier, often used for cache. |
| **Registers / CPU cache** | Very fast storage close to/in CPU for execution. |
| **Virtual memory** | Extends apparent memory using paging/swap; may put sensitive RAM contents on disk. |
| **SSD wear leveling** | Distributes writes; ordinary overwrites may miss remapped/reserved blocks. |

- **Cold boot attack:** Attempts to recover sensitive content, such as encryption keys, from RAM before residual charge decays.
- **Data remanence:** Data remains recoverable after ordinary deletion or ineffective overwriting. Apply appropriate media sanitization, encryption, or destruction (**Chapter 5**).
- **Full-disk encryption (FDE):** Reduces disclosure if a laptop or storage device is stolen; protect keys as well.
- **Sequential vs. random access:** Tape is typically sequential; disks/SSDs permit random access.
- **Lower-priority architecture terms:** *Immediate addressing* = value in instruction; *direct* = address in instruction; *indirect* = address points to another address; *base + offset* = computed address; *register* = CPU register operand.

## 4. Emanations, Peripheral Devices, and Firmware

- **EMSEC / TEMPEST:** Protection against information leakage through unintended electromagnetic emissions (also called **Van Eck phreaking** when intercepted).
- **Countermeasures:** Faraday cage, shielding/shielded cables, distance/control zones, and masking/white noise.
- **Peripheral risks:** Printers may store confidential jobs; monitors can be observed or intercepted; keyboards can be bugged; legacy modems or mobile hotspots can bypass perimeter filtering.
- **Exam clue:** Sensitive information inferred from electromagnetic radiation → **TEMPEST/EMSEC**, not conventional network eavesdropping.

### Firmware boot security

| Term | Essential meaning |
|---|---|
| **BIOS / UEFI** | Firmware initializes hardware and starts boot; UEFI is the modern replacement. |
| **Flashing** | Updating firmware. |
| **Phlashing** | Malicious firmware modification/replacement. |
| **Secure Boot** | Checks digital signatures/trust of boot components; aims to **block** unauthorized boot code. |
| **Measured Boot** | Measures/hashes boot components and stores measurements using the **TPM**; supports later integrity **verification**, rather than blocking boot by itself. |
| **Root of Trust (RoT)** | Trusted starting point/anchor for establishing security of subsequent components. |
| **TPM / HSM** | Hardware-backed cryptographic operations and key protection; TPM often supports device/boot integrity mechanisms. |

**Exam distinction:** **Secure Boot = prevent untrusted boot components from loading; Measured Boot = record measurements for verification.** Neither makes firmware invulnerable.

## 5. Client, Server, and Distributed Architecture Risks

- **Client-side attacks:** Malicious pages/scripts, browser flaws, mobile code, cached malicious content, phishing, and compromised extensions.
- **Mobile code:** Code delivered from a remote source and executed on the client; historic examples are **Java applets** and **ActiveX** (legacy). JavaScript remains broadly used but is generally browser-sandboxed.
- **Same-Origin Policy (SOP):** Restricts a script from reading data from a different **scheme + hostname + port** origin (subject to specific browser mechanisms such as CORS).
- **Browser controls:** Patch browsers, limit extensions, use script isolation, and apply **Content Security Policy (CSP)** to constrain resource/script loading. XSS/CSRF details belong in Chapter 21.
- **Local cache poisoning:** Malicious content substituted into stored browser/DNS/ARP data; maintain patching and cache protections.
- **Server-side flow control:** Prevent congestion/resource exhaustion. **Load balancing** distributes traffic, improves utilization and availability; does not replace access controls.
- **Distributed systems:** Many coordinated components can improve resilience, but increase attack surface and introduce **lateral movement, inconsistent patching, weak service authentication, logging gaps, and cross-border compliance** risks.
- **Distributed controls:** Strong service identity, least privilege, encrypted links, segmentation, standardized hardening, centralized logs/monitoring.

### Computing approaches — quick distinctions

| Term | Distinction / risk |
|---|---|
| **SMP** | Symmetric multiprocessing: processors generally share an OS and memory. |
| **AMP** | Asymmetric multiprocessing: processors have differentiated/independent roles or resources. |
| **MPP / HPC** | Massive parallel/high-performance computation; compute + network + storage bottlenecks and availability matter. |
| **Grid computing** | Loosely coordinated, often changing nodes; confidentiality, result integrity, and predictability are challenges. |
| **P2P** | Peers directly share resources without relying on one central coordinator; weaker centralized oversight, content/control risks. |
| **RTOS** | Real-time operating system: predictable timing; **hard real-time** misses deadlines = unacceptable, **soft real-time** tolerates some delay. |

## 6. Industrial Control and Operational Technology (OT/ICS)

| System | Purpose | Example |
|---|---|---|
| **PLC** | Controls a specific machine/industrial function. | Automated valve or conveyor controller. |
| **DCS** | Distributed control within an industrial plant/process. | Chemical plant control system. |
| **SCADA** | Supervisory monitoring/control across geographically spread assets. | Regional electric power grid. |
| **HMI** | Human–machine interface for operators. | Control-room monitoring display. |
| **Modbus** | Widely used industrial communication protocol. | PLC/device communications. |

- **Primary priorities:** Human **safety** and **availability/reliability of real-time control**, with integrity also critical; confidentiality may be secondary in many OT scenarios.
- **Typical weaknesses:** Long-lived legacy equipment, default credentials, weak/absent authentication, insecure protocols, difficult patching, and unsafe IT/OT connectivity.
- **Controls:** IT/OT segmentation or isolation, allowlisted communications, restricted remote access, strong credentials, monitoring, change-control/testing before patching.
- **Standards:** **IEC 62443** and **NIST SP 800-82** for ICS/OT security.
- **Exam clue:** Avoid blindly applying IT controls that disrupt critical industrial operations; preserve **safety and availability**.

## 7. IoT, Embedded, Edge, Fog, and Static Systems

| Term | Simple differentiation |
|---|---|
| **IoT** | Network-connected smart devices (sensors, cameras, thermostats). |
| **IIoT** | IoT applied to industrial automation/monitoring. |
| **Embedded system** | Computing component integrated into a larger device for dedicated functions. |
| **Cyber-physical system** | Computing/sensing that directly interacts with or controls physical processes. |
| **Edge computing** | Processes data **at or near the device/data source**. |
| **Fog computing** | Processes data at an **intermediate local/LAN gateway or layer**, between devices and central cloud. |
| **Static/nonpersistent system** | Changes are restricted or discarded/reset to a known state (e.g., kiosk/guest desktop). |

- **Common risks:** Low resources, weak encryption, hard-coded credentials, vendor dependence, outdated firmware, lack of patch support, and physical-safety consequences.
- **Controls:** Device inventory, vendor assessment, unique credentials, signed/verified updates where supported, network segmentation, disable unnecessary services, monitor externally if the device cannot log reliably.
- **Exam clue:** Can't reliably patch an embedded/OT device? Prioritize **isolation, restricted communication, monitoring, compensating controls**.

## 8. Microservices, APIs, IaC, and Immutable Infrastructure

- **Microservices:** Small independently deployed services connected through APIs. Benefits: modularity and scaling; risks: **more APIs, credentials, network paths, service-to-service trust, and monitoring complexity**.
- **Key controls:** Service authentication and authorization, TLS/mTLS where appropriate, API gateway, input validation, encryption, secrets management, logging, image scanning, least privilege.
- **SOA:** Builds functions from reusable services; integrated applications can have unexpected security weaknesses.
- **IaC (Infrastructure as Code):** Infrastructure configuration expressed in versioned, testable code. Security: peer review, configuration scanning, secrets protection, controlled changes, drift detection.
- **Immutable infrastructure:** **Replace/redeploy** a server or workload with a newly built image rather than patching it manually in place. Improves consistency; underlying images must still be patched and trusted.

## 9. Virtualization and Container Security

| Topic | Exam distinction |
|---|---|
| **Type 1 hypervisor** | Bare-metal, runs directly on host hardware. |
| **Type 2 hypervisor** | Hosted; runs over an existing operating system. |
| **Virtual machine (VM)** | Has its own guest OS and isolation boundary managed by hypervisor. |
| **Container** | Shares the host OS kernel; packages application and dependencies, typically lighter than a VM. |
| **VM escape** | Compromised guest crosses isolation into host/hypervisor or other guests. |
| **VM sprawl** | Uncontrolled proliferation of VMs; patching, ownership, licensing, and inventory gaps. |
| **VDI** | Desktops run centrally; endpoints access them remotely. |
| **Persistent VDI** | Desktop changes persist. |
| **Nonpersistent VDI** | Desktop resets to a standard state after session. |
| **Scalability** | Ability to handle increased workloads. |
| **Elasticity** | Automatically/quickly expands **and contracts** resources to match demand. |

- **Hypervisor compromise is high-impact** because multiple VMs depend on it; harden and patch both **host/hypervisor and each guest OS**.
- **Container controls:** Trusted/signed images, vulnerability scanning, minimal privileges, avoid privileged containers, runtime monitoring, network segmentation, secrets management, and kernel/host hardening.
- **Container distinction:** Containers do **not** provide the same default isolation boundary as full VMs because they share the kernel.
- **Snapshots are useful for recovery but should not automatically be treated as a complete, independent backup strategy.**
- **Shadow IT:** Unapproved technology outside normal management; may include cloud services, VMs, and endpoints.


## 10. Mobile Device Security and Management

| Technology | Main Function |
|---|---|
| **MDM – Mobile Device Management** | Manages device configurations, compliance, remote wipe, and apps. |
| **MAM – Mobile Application Management** | Manages **applications** and their business data rather than the entire device. |
| **MCM – Mobile Content Management** | Manages mobile access to and handling of corporate **content**. |
| **UEM – Unified Endpoint Management** | Centralized management of mobile devices, PCs, and other endpoint types. |
| **FDE – Full-Device Encryption** | Encrypts stored device data against offline theft; not a cure for unlocked or compromised devices. |
| **Remote Wipe** | Attempts to erase data remotely; may fail if the device cannot receive the command. |
| **Geotagging** | Embeds geographical location information in files/media (privacy risk). |
| **Geofencing** | Enables policies/actions based on whether a device is inside or outside a defined geographical boundary. |
| **Sideloading** | Installs apps outside the normal app store/deployment path (greater security risk). |
| **Rooting / Jailbreaking** | Bypasses device restrictions to gain elevated privileges (higher security risk). |
| **Carrier Unlocking** | Allows switching telecommunications providers; **not the same as rooting**. |
| **Application Allowlisting** | Only preapproved applications may execute; **default deny**. |

**Easy Memory:**
- **MDM → Device**
- **MAM → Application**
- **MCM → Content**
- **UEM → All Endpoints**
- **FDE → Encryption of Device Storage**

**CISSP Exam Clue:** Identify whether the requirement is to manage the entire device (MDM), applications only (MAM), corporate content (MCM), or multiple endpoint types (UEM).



### Device Ownership Policies

| Model | Full Form | Ownership / Permitted Use | Key Risk |
|---|---|---|---|
| **BYOD** | **Bring Your Own Device** | Employee-owned; personal + business use. | Highest device variability, privacy concerns, and difficulty separating business/personal data. |
| **CYOD** | **Choose Your Own Device** | Employee chooses from an organization-approved device list; ownership depends on policy. | Better standardization, but ownership and management responsibilities must be clarified. |
| **COPE** | **Corporate-Owned, Personally Enabled** | Company-owned; both business and personal use permitted. | Better organizational control, but business and personal data coexist. |
| **COBO** | **Corporate-Owned, Business-Only** | Company-owned; exclusively for business use. | Strong separation and control, but employees may need a separate personal device. |
| **COMS** | **Corporate-Owned Mobile Strategy** | Company-owned devices restricted to business activities (similar to COBO). | Stronger security and centralized management; limited personal flexibility. |

**Easy Memory:**
- **BYOD → Bring your personal device.**
- **CYOD → Choose from approved devices.**
- **COPE → Company owns, personal use allowed.**
- **COBO / COMS → Company owns, business use only.**

**Mobile Security Safeguards:**
- **FDE (Full-Device Encryption):** Protects stored data if a device is lost or stolen.
- **MDM (Mobile Device Management):** Controls device configuration, compliance, applications, and remote wipe.
- **UEM (Unified Endpoint Management):** Centrally manages mobile devices, PCs, and other endpoints.
- **MAM (Mobile Application Management):** Controls corporate applications and their data.
- **MFA (Multifactor Authentication):** Strengthens authentication using multiple factors.
- **SMS (Short Message Service)-based 2FA (Two-Factor Authentication):** Better than passwords alone, but phishing-resistant methods such as security keys are preferred.
- **Application Allowlisting:** Only approved applications can execute.
- **Geofencing:** Enforces security policies based on device location.
- **Containerization / Storage Segmentation:** Separates corporate data from personal data.
- **Other Controls:** Strong screen locks, patch management, disabling unused features, and restricting removable storage and hotspots.

**Mobile Device Policy Requirements:**
- Define device and data ownership.
- Establish employee privacy and monitoring rules.
- Specify remote-wipe authorization and consent.
- Define incident investigation and digital forensic access.
- Establish technical support and maintenance responsibilities.
- Address legal obligations and acceptable use policies.

**CISSP Exam Clues:**
- **Highest organizational control and business/personal separation → COBO / COMS.**
- **Company-owned with personal use permitted → COPE.**
- **Employee selects from approved devices → CYOD.**
- **Employee-owned personal device used for work → BYOD.**
- **Lost or stolen mobile device → FDE + strong authentication + MDM + remote-wipe capability.**
- **Remote wipe alone is insufficient** because the device may be offline or unable to receive the command.


## 11. Core Architecture Attacks and Countermeasures

| Threat | What it means | Key defense |
|---|---|---|
| **Covert timing channel** | Leaks information by deliberately varying timing or resource use. | Monitor abnormal timing/behavior, reduce shared-resource leakage. |
| **Covert storage channel** | Leaks information through shared storage locations, e.g., slack space. | Resource isolation, permissions, monitoring. |
| **Backdoor / maintenance hook** | Hidden bypass of normal access controls. | Secure SDLC, code review, testing, remove test access. |
| **Rootkit** | Deeply embedded malware that hides itself and other activity. | Secure Boot, monitoring/integrity checks; rebuild from trusted media when necessary. |
| **Data diddling** | Subtle unauthorized modification of data during input/processing. | Integrity controls, validation, audit trails, separation of duties. |
| **Salami attack** | Repeated small deductions/thefts accumulate over time. | Transaction reconciliation, anomaly detection, separation of duties. |
| **Cold boot** | Attempts to recover residual secrets from RAM. | Physical security, strong device/key protections. |
| **VM escape** | Breaks out of guest isolation. | Patch/harden hypervisor, strong workload isolation. |
| **Phlashing** | Compromises firmware/boot foundation. | Signed firmware, verified updates, hardware root of trust. |

### Fast CISSP recall

1. **STIX = threat-intelligence language; TAXII = exchange mechanism.**
2. **Localization = where data resides; sovereignty = whose laws apply.**
3. **Ring 0 = kernel privilege; Ring 3 = user applications.**
4. **Secure Boot = block untrusted code; Measured Boot = measure and record.**
5. **TEMPEST/EMSEC = emanation leakage; Faraday cage = shielding.**
6. **ICS: safety/availability first; PLC = device, DCS = plant, SCADA = wide-area supervisory control.**
7. **Edge = near device; Fog = intermediate local layer.**
8. **Type 1 = bare metal; Type 2 = hosted; containers share kernel.**
9. **VM escape = isolation failure; VM sprawl = governance/inventory failure.**
10. **Covert timing = time changes; covert storage = shared storage changes.**
11. **Data diddling = alter data; salami = repeatedly steal tiny amounts.**
12. **BYOD = personal device; COPE = company device with personal use; COBO = business only.**
